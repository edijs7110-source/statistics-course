The machine-learning workflow

From raw data to a model you’d deploy, without leaks

Put the whole module together with tidymodels: spend the data on a stratified training and test split, write the preprocessing as a recipe that’s re-learned inside every fold, specify a lasso logistic regression, bundle them in a workflow, and tune the penalty with folds that keep each pump’s records together. Then fit the final model once, test it once, explain it with permutation importance, and check that it serves both sites equally well.

Module 7 · Lesson 14 of 14 Week 117 of 160 About 5–7 hours

This module has used a dozen methods, and every one of them came with the same chores: split the data, preprocess it (inside each fold, to avoid leakage), set up cross-validation (with the right folds), tune, refit, test once, check. Each lesson wrote those chores by hand, in a slightly different way. That’s fine for learning, and error-prone for real work.

tidymodels is a set of R packages that gives each chore its own tool, with a consistent grammar:

Package Chore Main functions
rsample splitting and resampling initial_split(), vfold_cv(), group_vfold_cv()
recipes preprocessing recipe(), step_*(), prep(), bake()
parsnip model specification logistic_reg(), set_engine()
workflows bundling recipe and model workflow(), add_recipe(), add_model()
tune, dials tuning tune(), tune_grid(), select_best()
yardstick metrics roc_auc(), metric_set()

This lesson rebuilds Lesson 6’s pump-failure model the tidymodels way, end to end, and adds the two last steps a model needs before anyone relies on it: an explanation of what it uses, and a check that it works for everyone it will serve.

The last lesson of the module, and the one you’ll use most in real projects! Same statistics, but organized so that the leaks we hunted in Lesson 2 can’t sneak in.

In this lesson you’ll:

  • split the data with a stratified initial split
  • write the preprocessing as a recipe: imputation, dummy variables and standardization
  • make cross-validation folds that keep each pump’s records together
  • specify, bundle and tune a lasso logistic regression
  • fit the final model once and evaluate it once on the test set, with last_fit()
  • explain the model with permutation importance, and check its calibration at each site

Spending the data

The setup code reads the pump data and makes the response a factor, failed, with “yes” as its first level (yardstick treats the first level as the event of interest). Unlike Lesson 6, it keeps the 125 records with a missing bearing temperature: the recipe will deal with them. It then builds everything this lesson uses, step by step, so that each exercise can start from it; the exercises rebuild the pieces one at a time.

The test set is set aside first, and touched once, at the very end. With rare failures, a purely random split could leave the test set with noticeably more or fewer failures than the training set, so the split is stratified: it samples within each class separately, keeping the failure rate the same in both.

Your turn. Split the data 75/25, stratified by failed, and compare the sizes and the failure rates of the two sets.

Stratify by the response, failed.

set.seed(7141)
split <- initial_split(pumps, prop = 0.75, strata = failed)
train <- training(split)
test <- testing(split)
c(n_train = nrow(train), n_test = nrow(test),
  rate_train = mean(train$failed == "yes"), rate_test = mean(test$failed == "yes"))

2,250 records for training and 750 for testing, with failure rates of 6.8% and 6.7%: matched, as stratification promises. Everything that follows (preprocessing, tuning, choosing the model) uses only the 2,250 training records.

Preprocessing as a recipe

A recipe lists the preprocessing steps, in order, without doing them yet:

  • update_role(record, pump, new_role = "id") keeps the record and pump identifiers in the data but out of the model;
  • step_impute_median() fills in missing bearing temperatures with the training median;
  • step_dummy() turns the categorical predictors (site and pump type) into 0/1 columns;
  • step_normalize() standardizes every numeric predictor.

prep() learns what each step needs (the median, the means and SDs) from the data it’s given; bake() applies them, to that data or to new data. Inside cross-validation, tidymodels preps the recipe on each fold’s analysis set only, so the held-out records never influence the medians or the SDs. That’s Lesson 2’s rule, enforced automatically.

Your turn. Prep the recipe on the training set, bake it, and check that no missing values remain. Also find the median the imputation step learned.

new_data = NULL returns the processed training data.

prepped <- prep(rec, training = train)
baked <- bake(prepped, new_data = NULL)
print(names(baked))
c(missing_before = sum(is.na(train$bearing_temp_C)), missing_after = sum(is.na(baked)),
  median_used = prepped$steps[[1]]$medians$bearing_temp_C)

125 missing bearing temperatures before, none after: each was filled with the training median, 57.8 °C. The baked data has the identifiers, the five numeric predictors (now standardized), the response, and three dummy columns: site_South, pump_type_multistage and pump_type_screw (centrifugal and North are the baselines). Module 1’s lessons on missing data would point out that median imputation is crude; step_impute_bag() or step_impute_knn() are better ones, and drop into the same recipe.

Folds that respect the pumps

The 2,250 training records come from 125 pumps, about 18 records each, and a pump’s records are alike: the same pump type, similar vibration levels from month to month. With random folds, a pump’s other months would sit in the analysis set while some of its months are held out, and the model would be judged partly on pumps it has already seen. The model will be used on next month’s records of the same pumps, so this leak is milder than Lesson 2’s, but a model that’s meant to work on newly installed pumps needs grouped folds, which hold out whole pumps.

Your turn. Make 5 folds grouped by pump, and check that no pump appears in both the analysis and the assessment set of any fold.

Group by pump.

set.seed(7142)
folds <- group_vfold_cv(train, group = pump, v = 5)
sapply(folds$splits, function(s) length(intersect(analysis(s)$pump, assessment(s)$pump)))

0, 0, 0, 0, 0: every fold holds out about 25 whole pumps. In rsample, “analysis” and “assessment” are the names for a fold’s training and held-out parts, to keep them distinct from the overall training and test sets.

Model, workflow and tuning

A parsnip model specification says what model to fit, not how: logistic_reg(penalty = tune(), mixture = 1) is a lasso logistic regression (glmnet’s alpha is parsnip’s mixture), with the penalty marked as a parameter to tune; set_engine("glmnet") says which package fits it. A workflow bundles the recipe and the model, so that they’re always prepped, fitted and applied together. tune_grid() then cross-validates the workflow at every value in a grid, re-prepping the recipe in each fold.

Your turn. Tune the workflow over the grid of 10 penalties from 10^{-4} to 10^{-1}, with the grouped folds, scoring by AUC. Look at the best mean AUCs.

Resample with the grouped folds, folds.

res <- tune_grid(wf, resamples = folds, grid = grid, metrics = metric_set(roc_auc))
show_best(res, metric = "roc_auc", n = 3)

The best penalty is 0.0022, with a mean CV AUC of 0.892 (standard error 0.018). Every penalty up to 0.01 is within 0.004 of it, and the AUC falls only above that, to 0.863 at 0.1, as the lasso drops predictors. collect_metrics(res) gives the whole table, and autoplot(res) plots it.

Your turn. select_best() picks the penalty with the highest mean AUC. select_by_one_std_err() applies the one-standard-error rule: it sorts the candidates from simplest to most complex (here, from the largest penalty down) and picks the first within one standard error of the best. Find both.

The simplest model has the largest penalty: sort by desc(penalty).

res <- tune_grid(wf, resamples = folds, grid = grid, metrics = metric_set(roc_auc))
c(best = select_best(res, metric = "roc_auc")$penalty,
  one_se = select_by_one_std_err(res, desc(penalty), metric = "roc_auc")$penalty)

0.0022 for the best, and 0.022, ten times more shrinkage, by the one-standard-error rule, with a mean AUC of 0.877. The rest of the lesson uses the best value: with failures this costly, a few points of AUC matter more than a simpler model.

The final fit, and the one test

With the penalty chosen, finalize_workflow() writes it into the workflow, and last_fit() does the last two steps in one call: it fits the workflow to the whole training set, and evaluates it, once, on the test set.

Your turn. Finalize the workflow with the best penalty, 0.00215, run last_fit(), and find the test AUC.

last_fit() takes the initial split, split, so it knows which rows are training and which are test.

final_wf <- finalize_workflow(wf, data.frame(penalty = 0.00215443469))
lf <- last_fit(final_wf, split = split, metrics = metric_set(roc_auc))
collect_metrics(lf)$.estimate

A test AUC of 0.885, close to the CV estimate of 0.892, as it should be when nothing has leaked. That number is the honest estimate to report. If you now went back and changed the model to improve it, the test set would become part of the tuning, and you’d need new data to get an honest estimate again. collect_predictions(lf) has the test-set probabilities, and extract_workflow(lf) the fitted workflow, ready to predict new records.

Explaining the model

A model that will decide which pumps get inspected needs an explanation that the reliability team can check against their experience. For a penalized linear model, the coefficients are one explanation.

Your turn. Extract the fitted model and look at its coefficients with tidy().

Extract the model from the last fit, lf.

lf <- last_fit(finalize_workflow(wf, data.frame(penalty = 0.00215443469)), split, metrics = metric_set(roc_auc))
co <- tidy(extract_fit_parsnip(lf))
setNames(round(co$estimate, 3), co$term)

The vibration coefficient is -1.47, the bearing temperature -0.48, the hours since service -0.39, and South -0.67. They’re negative because glmnet models the probability of the second level of the response, “no”, so every sign is flipped: on the failure scale, vibration is +1.47 per SD. It’s an easy trap. And since the predictors are standardized, the sizes are comparable: vibration matters three times as much as anything else. The motor current, the seal flush and the pump types have coefficients near zero.

Coefficients only explain models that have them. Permutation importance works for any model: shuffle one predictor’s values in the test set, breaking its link with the response, and see how much the model’s AUC drops. A big drop means the model relies on that predictor.

Your turn. Compute the permutation importance of each of the seven predictors.

Shuffle the predictor’s own column: shuffled[[v]].

lf <- last_fit(finalize_workflow(wf, data.frame(penalty = 0.00215443469)), split, metrics = metric_set(roc_auc))
final <- extract_workflow(lf)
auc_of <- function(d) roc_auc_vec(d$failed, predict(final, d, type = "prob")$.pred_yes)
base <- auc_of(test)
preds <- c("vibration_mm_s", "bearing_temp_C", "hours_since_service", "site", "pump_type", "motor_current_pct", "seal_flush_bar")
sapply(preds, function(v) {
  set.seed(7143)
  shuffled <- test
  shuffled[[v]] <- sample(shuffled[[v]])
  base - auc_of(shuffled)
})

Shuffling the vibration drops the AUC by 0.29, from 0.885 to about 0.60. The hours since service (0.019), the bearing temperature (0.014) and the site (0.008) matter a little, and the rest not at all. The model is, above all, a vibration alarm with corrections, which the reliability team will find reassuring: it’s what their own experience says. One shuffle is noisy; repeating each one several times and averaging is better practice (the iml package does this, with FeatureImp()).

NoteGo deeper: other ways to explain a model

Permutation importance says how much a model relies on each predictor, not how. Partial dependence plots show how the average prediction changes as one predictor varies, with the others held at their observed values: a model-agnostic version of Lesson 9’s partial effects. SHAP values split each single prediction into contributions from each predictor, which is useful for explaining one decision (“this pump was flagged mainly because of its vibration”). Module 8 uses both for tree ensembles, where there are no coefficients to read. Christoph Molnar’s free book Interpretable Machine Learning covers all of them, with their pitfalls: with correlated predictors, shuffling one creates impossible combinations (a hot bearing on a calm pump), and the importances can mislead.

Does it work for everyone?

An overall AUC can hide a group that the model serves badly, as Lesson 6 found for the South site. The last check before deployment is to compare the model’s performance across the groups it will be used on: sites, pump types, shifts, or, for models about people, groups of people. The questions are always the same: are the predictions calibrated in each group, and does each group get the same sensitivity at the chosen threshold?

Your turn. For each site, compare the average predicted failure probability with the observed failure rate in the test set, and find the sensitivity at Lesson 6’s cost-based threshold of 0.04.

Use the threshold 0.04.

lf <- last_fit(finalize_workflow(wf, data.frame(penalty = 0.00215443469)), split, metrics = metric_set(roc_auc))
p <- predict(extract_workflow(lf), test, type = "prob")$.pred_yes
by_site <- function(p) sapply(c("North", "South"), function(s) {
  k <- test$site == s
  c(predicted = mean(p[k]), observed = mean(test$failed[k] == "yes"),
    sensitivity = mean(p[k & test$failed == "yes"] >= 0.04))
})
round(by_site(p), 3)

Well calibrated at both sites: 7.1% predicted against 6.7% observed at North, and 7.1% against 6.6% at South. At a threshold of 0.04, the model catches 77% of North’s failures and 90% of South’s. Unlike Lesson 6’s model, this one includes the site as a predictor, and its South coefficient corrects for the South sensors’ low readings. Including the group variable was the right fix here, because the group difference is a measurement artifact with a known cause. In models about people, using a group variable can be illegal or harmful, and the fixes are harder; the check, though, is the same.

Challenge round

Challenge 1 · Without the site. Remove the site from the model by adding step_rm(site_South) to the recipe (after the dummy step has made that column), refit with a penalty of 0.001 (the best for that model), and repeat the comparison by site. Also find its test AUC.

Remove the dummy column site_South.

rec_ns <- rec |> step_rm(site_South)
wf_ns <- workflow() |> add_recipe(rec_ns) |> add_model(spec)
lf_ns <- last_fit(finalize_workflow(wf_ns, data.frame(penalty = 0.001)), split, metrics = metric_set(roc_auc))
p <- predict(extract_workflow(lf_ns), test, type = "prob")$.pred_yes
print(collect_metrics(lf_ns)$.estimate)
round(sapply(c("North", "South"), function(s) {
  k <- test$site == s
  c(predicted = mean(p[k]), observed = mean(test$failed[k] == "yes"))
}), 3)

A test AUC of 0.886, the same as the model with the site (0.885). By the usual headline metric, the two models are equally good. But without the site, the model predicts 9.4% failures at North, where 6.7% failed, and 4.6% at South, where 6.6% failed: it under-predicts South by a third and over-predicts North. The AUC can’t see this, because within each site the ranking of the pumps is still good; only the probabilities are off, in opposite directions. With cost-based thresholds, that means too many inspections at North and too few at South. Two models, one number, and only a check by group tells them apart.

Challenge 2 · What it saves. Using the final model’s test-set predictions from collect_predictions(), find the cost of inspecting every pump with \hat p \ge 0.04 (€800 per inspection, €20,000 per missed failure), and compare it with inspecting none and inspecting all.

The threshold is 0.04.

lf <- last_fit(finalize_workflow(wf, data.frame(penalty = 0.00215443469)), split, metrics = metric_set(roc_auc))
pr <- collect_predictions(lf)
y <- pr$failed == "yes"
flag <- pr$.pred_yes >= 0.04
c(model = 800 * sum(flag) + 20000 * sum(!flag & y), none = 20000 * sum(y), all = 800 * length(y))

€360,800 with the model, against €1.0 million for inspecting nothing and €600,000 for inspecting everything: a saving of €239,000 over the better simple policy, on 750 pump-months, about €320 per pump-month. That’s the number that gets a model deployed. Like every number from the test set, it’s an estimate with an uncertainty (only 50 failures), and the bootstrap of Lesson 2 could put an interval on it.

Quick quiz

1. Why stratify the initial split by the response?

With rare events, a random split can give the test set noticeably more or fewer of them.

2. What’s the difference between prep() and bake()?

Inside resampling, the recipe is prepped on each fold’s analysis set only.

3. Why group the folds by pump?

It’s Lesson 2’s grouped CV, with group_vfold_cv().

4. What does last_fit() do?

For deployment, some practitioners then refit on all the data; the test estimate stays the one from last_fit().

5. How does permutation importance work?

It works for any model, which is why it’s so widely used.

6. Two models have the same test AUC, but one is well calibrated at both sites and the other under-predicts one site by a third. What does that show?

Subgroup checks of calibration and sensitivity are part of evaluating any model before it’s used.

Wrap-up

You’ve put the whole machine-learning workflow together. Here’s what you’ve learned:

  • Spend the data once: a stratified 75/25 split, with the test set untouched until the end.
  • Recipes hold the preprocessing (imputation, dummies, standardization), and tidymodels re-learns them inside every fold, so the leaks of Lesson 2 can’t happen.
  • Grouped folds held out whole pumps. Workflows bundled the recipe and a lasso logistic model, and tune_grid() chose a penalty of 0.0022, with a CV AUC of 0.892.
  • last_fit() gave the honest test AUC, 0.885.
  • Explanation: permutation importance showed a model that’s mostly a vibration alarm, which matches the engineers’ experience.
  • Fairness: with the site included, the model was calibrated at both sites. Without it, the overall AUC was unchanged, but South’s failures were under-predicted by a third.
  • The business case: the model would have cost €360,800 on the test set, against €600,000 for inspecting every pump.

NoteKey words from this lesson
tidymodels
A collection of R packages for modeling that share a consistent grammar: rsample, recipes, parsnip, workflows, tune, dials and yardstick, among others.
Stratified split
A split that samples within each class separately, so that every part has the same class proportions.
Recipe
A specification of preprocessing steps that’s learned (prep()) from training data and applied (bake()) to any data.
Model specification
A description of a model’s type, its parameters and the engine that fits it, separate from the data.
Workflow
A bundle of a recipe and a model that’s fitted and applied as one object.
Analysis and assessment sets
The parts of a resampling fold used to fit and to evaluate a model.
Permutation importance
The drop in a model’s performance when one predictor’s values are randomly shuffled.
Subgroup evaluation
Checking a model’s calibration, error rates and sensitivity separately for each group it will be used on.
