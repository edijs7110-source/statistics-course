Working across statistical software

Reading SAS, SPSS and Stata code, and moving data and results between tools

Read programs written for SAS, SPSS and Stata, translate common procedures into R, understand why the same analysis can give different numbers in different software, and move data and results between tools safely.

Module 1 · Lesson 14 of 14 Week 29 of 160 About 5–7 hours

Statisticians rarely work in one language alone. A colleague from the pharmaceutical side sends you a SAS program, the quality team keeps its analyses in SPSS, and an economist down the hall swears by Stata. You don’t need to master all three. But you do need to read their code, reproduce their numbers in R, and pass data and results back and forth without anything getting lost. This last lesson of the module shows you how, and warns you about the traps where the same analysis gives different answers.

Think of it as learning to read a few dialects. You don’t need to speak them fluently, just enough to follow the conversation, and to notice when something gets lost in translation!

In this lesson you’ll:

  • recognize the same data steps in SAS, SPSS, Stata and R
  • read short SAS programs, SPSS syntax and Stata do-files, and translate them into R
  • understand why software can disagree: missing values, quantiles, rounding and reference levels
  • move data between tools without losing labels or values
  • share results that others can use and check

One analysis, four languages

All four languages do the same jobs, with different words. Here’s a phrasebook:

Task SAS SPSS Stata R
Open a dataset SET plant.batches; GET FILE='batches.sav'. use batches.dta read_csv(), read_sav(), read_dta()
Make a variable y = x / 100; COMPUTE y = x / 100. generate y = x / 100 mutate(y = x / 100)
Change values IF x > 5 THEN y = 1; RECODE x (1 2 = 1) INTO y. replace y = 1 if x > 5 mutate() with if_else() or case_when()
Keep rows WHERE x > 5; SELECT IF x > 5. keep if x > 5 filter(x > 5)
Sort PROC SORT; BY x; SORT CASES BY x. sort x arrange(x)
Summarize by group PROC MEANS; CLASS g; VAR x; MEANS TABLES=x BY g. tabstat x, by(g) statistics(n mean sd) group_by(g) |> summarise()
Count PROC FREQ; TABLES a*b; CROSSTABS a BY b. tabulate a b count(a, b)
Regression PROC REG; MODEL y = x1 x2; REGRESSION /DEPENDENT y /METHOD=ENTER x1 x2. regress y x1 x2 lm(y ~ x1 + x2)
Merge MERGE a b; BY id; MATCH FILES /FILE=* /TABLE='b.sav' /BY id. merge 1:1 id using b left_join(a, b, by = "id")

A few habits show at once. SAS and SPSS end every statement with punctuation, a semicolon or a period. SAS, SPSS and Stata all work on one “current” dataset at a time, while R can hold as many data frames as you like. And SAS and SPSS don’t care about upper and lower case in their commands, while R and Stata do.

Reading SAS

A SAS program is made of steps. A DATA step builds a dataset, row by row. A PROC step (short for procedure) analyzes one. Each step ends with RUN;. Here’s a typical program:

DATA work.hot;
  SET plant.batches;          /* read the batches table */
  WHERE temp_C > 180;         /* keep the hot batches */
  yield_frac = yield_pct / 100;
RUN;

PROC MEANS DATA=work.hot N MEAN STD MAXDEC=2;
  CLASS catalyst;             /* one row per catalyst */
  VAR yield_pct;              /* summarize the yield */
RUN;

plant.batches means “the dataset batches in the library plant”, where a library is a folder of SAS datasets. work is the temporary library, which is deleted at the end of the session. Comments go between /* and */. MAXDEC=2 rounds the output to two decimals. In R, the whole program is one pipeline:

batches |>
  filter(temp_C > 180) |>
  mutate(yield_frac = yield_pct / 100) |>
  group_by(catalyst) |>
  summarise(n = n(), mean = round(mean(yield_pct), 2), sd = round(sd(yield_pct), 2))
#> # A tibble: 4 × 4
#>   catalyst     n  mean    sd
#>   <chr>    <int> <dbl> <dbl>
#> 1 A            5  57.5  1.89
#> 2 B            6  55.9 13.5 
#> 3 C            2  65.2  0   
#> 4 D            2  65.1 12.6

Your turn. Translate this SAS procedure into R. (batches is ready in every exercise.)

PROC MEANS DATA=plant.batches N MEAN STD MIN MAX;
  CLASS reactor;
  VAR residence_min;
RUN;

The CLASS statement names the grouping variable, and VAR names the variable to summarize. Group by reactor.

batches |>
  group_by(reactor) |>
  summarise(n = n(), mean = mean(residence_min), sd = sd(residence_min),
            min = min(residence_min), max = max(residence_min))

R1’s batches stayed in the reactor about 5 minutes longer, on average: 47.4 against 42.2 minutes.

Reading SPSS syntax

SPSS is mostly used through menus, but every menu action can be pasted as syntax, and analysts often share syntax files (.sps). Each command ends with a period, and options follow slashes:

GET FILE='operator_survey.sav'.
FREQUENCIES VARIABLES=role shift.
MEANS TABLES=overtime_h BY role
  /CELLS=COUNT MEAN STDDEV.
RECODE workload (1 2 = 1) (3 = 2) (4 5 = 3) INTO workload3.
VALUE LABELS workload3 1 'low' 2 'about right' 3 'high'.

FREQUENCIES counts each value, MEANS ... BY summarizes one variable by another, and RECODE ... INTO makes a new variable from an old one, leaving the original as it was. In R, with haven:

survey <- read_sav("data/operator_survey.sav")
count(survey, role = as_factor(role))
#> # A tibble: 3 × 2
#>   role           n
#>   <fct>      <int>
#> 1 operator      24
#> 2 technician    15
#> 3 engineer       9
survey |>
  mutate(workload3 = case_when(workload %in% 1:2 ~ "low",
                               workload == 3 ~ "about right",
                               workload %in% 4:5 ~ "high")) |>
  count(workload3)
#> # A tibble: 4 × 2
#>   workload3       n
#>   <chr>       <int>
#> 1 about right    18
#> 2 high           14
#> 3 low            13
#> 4 <NA>            3

Remember from Lesson 9 that read_sav() turns the user-defined missing code, 9 = “no answer”, into NA, so those three people end up in the NA row. In SPSS, the same three would be left out of the recode automatically, as missing. The results agree, but only because haven did the right thing for you.

Your turn. Translate MEANS TABLES=overtime_h BY shift. into R, with the shifts’ names.

shift is a labelled variable, so as_factor(shift) gives the names “day” and “night”.

survey |>
  group_by(shift = as_factor(shift)) |>
  summarise(n = n(), mean = mean(overtime_h), sd = sd(overtime_h))

About 7.1 hours of overtime on the day shift, and 7.6 on nights.

Reading Stata

Stata’s commands are short, and a script of them is called a do-file (.do). Most commands follow the same pattern: the command, the variables, then if conditions, and options after a comma:

use "batches.dta", clear
generate long_run = residence_min > 50
tabulate catalyst long_run
regress yield_pct temp_C residence_min

generate makes a new variable (replace changes an existing one), tabulate makes a frequency table, and regress fits a linear regression. clear throws away the dataset that was open before. In R:

stata <- read_dta("data/batches.dta")
stata |>
  mutate(long_run = residence_min > 50) |>
  count(catalyst, long_run)
#> # A tibble: 8 × 3
#>   catalyst long_run     n
#>   <chr>    <lgl>    <int>
#> 1 A        FALSE        6
#> 2 A        TRUE         4
#> 3 B        FALSE       10
#> 4 B        TRUE         2
#> 5 C        FALSE        7
#> 6 C        TRUE         2
#> 7 D        FALSE        5
#> 8 D        TRUE         4

Your turn. Translate regress yield_pct temp_C residence_min, and find the coefficient for the residence time.

In Stata, the first variable after regress is the outcome, and the rest are the predictors: yield_pct ~ temp_C + residence_min.

fit <- lm(yield_pct ~ temp_C + residence_min, data = batches)
coef(fit)

Each extra minute of residence time adds about 0.64 percentage points of yield. Both Stata and R quietly drop the two batches with no temperature, so nobs(fit) is 38, in both. Regression is the whole of the next module!

Same data, different numbers

Translate a program perfectly, and you can still get different numbers. Four differences cause most of the trouble.

1. Missing values in comparisons. Is a missing temperature less than 170? Each language answers differently:

Language Is NA < 170? Is NA > 185? So the missing values are…
R NA NA dropped by filter()
SPSS missing missing dropped by SELECT IF
SAS true false treated as smaller than every number
Stata false true treated as larger than every number

So SAS’s WHERE temp_C < 170; keeps the two batches with missing temperatures, and Stata’s generate hot = temp_C > 185 marks them as hot! Both are famous sources of bugs. A careful SAS or Stata programmer adds a condition like AND NOT MISSING(temp_C), or & !missing(temp_C) in Stata. When you reproduce someone’s numbers, check whether they did.

sum(batches$temp_C < 170, na.rm = TRUE)            # R and SPSS
#> [1] 6
sum(batches$temp_C < 170 | is.na(batches$temp_C))  # SAS
#> [1] 8

2. Quantiles. There are at least nine reasonable ways to compute a quartile from a sample, and software disagrees about which to use. R’s default is type 7, SAS’s default is type 2, and SPSS uses type 6. quantile() can do all of them:

quantile(batches$yield_pct, c(0.25, 0.5, 0.75), type = 7)   # R
#>    25%    50%    75% 
#> 55.200 57.300 63.125
quantile(batches$yield_pct, c(0.25, 0.5, 0.75), type = 2)   # SAS
#>   25%   50%   75% 
#> 55.10 57.30 63.25

The medians agree, but the quartiles differ in the first decimal place. That’s not an error, just a different definition, but it’s a puzzling difference if you don’t know about it.

3. Rounding. What’s 2.5, rounded to a whole number? SAS, SPSS, Stata and Excel all say 3. R says 2:

round(c(0.5, 1.5, 2.5, 3.5))
#> [1] 0 2 2 4

R follows the international standard for floating-point arithmetic (IEC 60559), which rounds a 5 to the even digit. Over many numbers, that avoids a slight upward bias. It rarely matters, but it explains the odd difference in the last digit of a table.

4. Reference levels. In a regression with a categorical predictor, one category is the baseline, and the coefficients compare the other categories with it. R and Stata use the first level as the baseline, while SAS’s PROC GLM and SPSS use the last. The fitted model is identical, but every coefficient looks different. You’ll meet this properly in the next module, and you’ll reproduce a SAS result in the challenge round.

Your turn. A colleague’s SPSS output gives the quartiles of the yield. Reproduce them in R.

SPSS uses type 6.

quantile(batches$yield_pct, c(0.25, 0.5, 0.75), type = 6)

55.0, 57.3 and 63.375, against R’s default of 55.2, 57.3 and 63.125.

Moving data and results

Data. haven writes files for every one of these tools, and it keeps the variable and value labels: write_sav(), write_dta() and write_xpt(). But each format has its own rules, and haven stops you when you break one:

  • SAS transport files, version 5 (the one regulators ask for), allow variable names of at most 8 characters. write_xpt(df, "file.xpt", version = 5) refuses residence_min, so you have to rename first.
  • Stata names can only use letters, digits and underscores, up to 32 characters, so yield.pct isn’t allowed.
  • SPSS’s user-defined missing values don’t exist in Stata. If you read a survey with user_na = TRUE, and write it to Stata, the 9 = “no answer” becomes an ordinary 9. Turn such codes into NA first, with zap_missing().

For tools beyond these three, like Python or a database, use CSV or Parquet (Lesson 9).

Results. When you send results to a colleague, send a table, not a screenshot. The broom package turns model output into a tidy data frame, which you can then write to CSV or Excel:

fit <- lm(yield_pct ~ temp_C + residence_min, data = batches)
broom::tidy(fit)
#> # A tibble: 3 × 5
#>   term          estimate std.error statistic      p.value
#>   <chr>            <dbl>     <dbl>     <dbl>        <dbl>
#> 1 (Intercept)      5.08    22.2        0.229 0.820       
#> 2 temp_C           0.132    0.124      1.06  0.296       
#> 3 residence_min    0.644    0.0960     6.71  0.0000000915

And whenever you can, send the code too. A result that someone else can re-run, in any language, is a result that they can trust.

Your turn. Save the survey as a Stata file, read it back, and check that the variable label of role survived the trip.

Read the file you just wrote: read_dta("survey.dta").

write_dta(survey, "survey.dta")
back <- read_dta("survey.dta")
attr(back$role, "label")

“Job role”: the variable label made it through, and so did the value labels. Try attr(back$role, "labels") to see them.

Challenge round

Challenge 1 · Reproduce a SAS result. A colleague ran this, and reported N = 8 and a mean yield of 55.68:

PROC MEANS DATA=plant.batches N MEAN;
  WHERE temp_C < 170;
  VAR yield_pct;
RUN;

Your R version gives N = 6. Make R reproduce the SAS result exactly, so that you can explain the difference to your colleague.

SAS treats a missing temperature as smaller than every number, so temp_C < 170 is true for the two batches with missing temperatures.

filter(temp_C < 170 | is.na(temp_C))

batches |>
  filter(temp_C < 170 | is.na(temp_C)) |>
  summarise(n = n(), mean = mean(yield_pct))

N = 8 and a mean of 55.675. The colleague’s “cool batches” include B07 and B23, whose temperatures are unknown, and B07 had one of the best yields of the campaign, 74.1%! Without the missing values, the six cool batches average 52.7%.

Challenge 2 · SAS’s baseline. A SAS colleague fitted the yield on the catalyst with PROC GLM; CLASS catalyst; MODEL yield_pct = catalyst / SOLUTION;, which uses the last catalyst, D, as the baseline. Their coefficient for catalyst A is −0.49. Reproduce it in R by making D the reference level.

The reference level is given as text: ref = "D".

batches |>
  mutate(catalyst = relevel(factor(catalyst), ref = "D")) |>
  lm(yield_pct ~ catalyst, data = _) |>
  coef()

Catalyst A’s coefficient is −0.49: its batches averaged 0.49 percentage points less than catalyst D’s. With R’s default baseline, A, the same model says that D is 0.49 more than A. Same model, same fit, different point of view. (The _ is the native pipe’s placeholder: it passes the data frame to the data argument.)

Quick quiz

1. In a SAS program, what does RUN; do?

SAS programs are made of steps, and each one ends with RUN;.

2. In Stata, a batch has a missing temperature. What does generate hot = temp_C > 185 give it?

A classic Stata trap. Add if !missing(temp_C), or the missing batches count as hot.

3. Which SAS statement keeps the batches with missing temperatures, as well as the cool ones?

In SAS, a missing number is smaller than every real number, so it passes any “less than” test.

4. You want R’s quartiles to match SPSS’s. Which quantile() type do you use?

SPSS (and Minitab) use type 6, and SAS’s default is type 2.

5. What does R’s round(2.5) give?

R rounds a 5 to the even digit, following the IEC 60559 standard. SAS, SPSS, Stata and Excel give 3.

6. SAS and R report different coefficients for the catalysts in the same regression. What’s the most likely reason?

The fitted models are identical. Only the baseline, and so the meaning of each coefficient, differs. relevel() changes R’s baseline.

Wrap-up

That’s the last lesson of Module 1, and only the project is left! You can read your colleagues’ code now, whatever their language. Here’s what you’ve learned:

  • The phrasebook: SAS’s DATA steps and PROCs, SPSS’s period-terminated commands, and Stata’s do-files all map onto dplyr verbs and lm().
  • Missing values: R and SPSS drop them in comparisons, SAS treats them as smaller than every number, and Stata as larger. Check for NOT MISSING() and !missing() when you reproduce results.
  • Definitions: quantiles (R type 7, SAS type 2, SPSS type 6), rounding (R rounds a 5 to the even digit), and baselines (R and Stata the first level, SAS and SPSS the last).
  • Moving data: haven’s writers keep labels. Respect each format’s naming rules, and turn user-defined missing codes into NA before you leave SPSS behind.
  • Sharing results: tidy tables from broom::tidy(), written to CSV or Excel, together with the code that made them.
TipPractice in RStudio (optional, about an hour)
  1. The translation workbook. UCLA’s statistical consulting pages show the same analyses in SAS, SPSS, Stata and R. Pick two of their SAS or Stata examples, translate them into R yourself, and then compare your version with theirs.
  2. Write for SAS. Write the batch table as a version 5 transport file. First rename every variable longer than 8 characters (for example, residence_min to res_min), and keep a small table that maps the new names to the old ones.
  3. A Stata round trip. Read the survey with user_na = TRUE, write it with write_dta(), and read it back. What happened to “no answer”? Repeat with zap_missing() before writing.
  4. Your own phrasebook. Start a one-page cheat sheet of the commands from this lesson, in all four languages. It’ll come in handy whenever a colleague sends you their code.
NoteKey words from this lesson
DATA step and PROC step
In SAS, a step that builds a dataset, and a step that runs an analysis procedure.
Syntax file
A script of SPSS commands, saved as .sps.
Do-file
A script of Stata commands, saved as .do.
Library
In SAS, a named folder of datasets, like plant in plant.batches.
Quantile type
One of the several definitions of a sample quantile. R’s default is type 7.
Reference level
The category that a regression compares the others with, also called the baseline.
Transport file
A SAS .xpt file, an open format for moving SAS datasets between systems.
