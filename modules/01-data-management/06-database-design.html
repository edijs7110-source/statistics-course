Entities, keys, normalization and data dictionaries

Use the relational model, draw entity-relationship diagrams, choose primary and foreign keys, normalize tables to store each fact once, and document data in a data dictionary.

In the last lesson you joined five tables, and it worked smoothly. That’s not luck: somebody designed those tables. Each one is about one kind of thing, each has a key, and each fact is stored exactly once. Compare that with the classic lab spreadsheet: one giant sheet, the supplier’s name typed again on every row, three results crammed into one cell, and “n/a” meaning something different in every column. This lesson is about designing data so that mistakes are hard to make, and questions are easy to answer.

Good database design is a bit like organizing a lab: a place for everything, and everything in its place. It takes a little thought up front, and then it saves you from a thousand small messes.

In this lesson you’ll:

  • describe data with the relational model: entities, attributes and relationships
  • read and draw entity-relationship diagrams
  • choose primary keys, including keys made of several columns
  • normalize tables, so that each fact is stored once
  • document data in a data dictionary

The relational model

Almost every database uses the relational model, invented by Edgar Codd at IBM in 1970. Its ideas are simple:

  • Data lives in tables, also called relations. Each table describes one kind of thing, an entity: a supplier, a lot, a batch, a lab result.
  • Each row is one instance of the entity, and each column is one of its attributes, like a lot’s delivery date.
  • Tables are connected by relationships, through keys: a batch uses a lot, a lot comes from a supplier.

The plant’s data is already designed this way. That’s why every table in Lesson 5 had a clear “one row per…”.

Entity-relationship diagrams

An entity-relationship diagram (ERD) is a picture of a database’s design: a box for each table, listing its columns, and lines for the relationships between them. Here’s the plant’s database:

PK marks a primary key and FK a foreign key. The ends of the lines are called crow’s feet, and they say how many rows can be on each side. || means “exactly one”, and o{ means “zero or more”. So reading the top line: each lot comes from exactly one supplier, and each supplier delivers zero or more lots. That’s a one-to-many relationship, the most common kind.

NoteGo deeper: many-to-many relationships

What if one batch could use several lots, and each lot could go into several batches? That’s many-to-many, and you can’t store it with a foreign key in either table. The standard fix is a third table, called a junction table, with one row per pair: batch_lots(batch_id, lot_id, kg_used). Each of its rows says “this batch used this much of this lot”. Both columns together form its primary key.

Choosing keys

A primary key must be unique and never missing. There are two kinds:

  • A natural key already means something, like a batch number B07 or a CAS number for a chemical.
  • A surrogate key is made up just to be an ID, like result_id (R0001, R0002, …). It never needs to change, even if everything else about the row does.

Sometimes no single column is unique, and the key is a composite key made of several columns together. In the lab results, is “batch plus analyte” enough to identify a result?

lab <- read.csv("data/lab_results.csv")
lab |> count(batch_id, analyte) |> filter(n > 1)
#>   batch_id analyte n
#> 1      B19  purity 2
#> 2      B21  purity 2
#> 3      B25  purity 2
#> 4      B34  purity 2
#> 5      B35  purity 2
#> 6      B39  purity 2

No: the six re-tested batches have two purity results each. Adding the measurement time makes it unique. That’s why the lab gave each result its own result_id: one simple column is much easier to work with than a key made of three.

Store IDs as text, even when they look like numbers. A lot number like 0042 stored as a number becomes 42, and suddenly it doesn’t match the label on the drum!

Normalization: store each fact once

Here’s the “one big table” version of the plant’s data, made by joining the batches with their lots and suppliers:

batches <- read.csv("data/batches.csv")
lots <- read.csv("data/lots.csv")
suppliers <- read.csv("data/suppliers.csv")
flat <- batches |> left_join(lots, by = "lot_id") |> left_join(suppliers, by = "supplier_id")
flat |> select(batch_id, lot_id, supplier_id, name, country) |> head(5)
#>   batch_id  lot_id supplier_id               name country
#> 1      B01 L26-001          S1 Fizzwell Chemicals     USA
#> 2      B02 L26-001          S1 Fizzwell Chemicals     USA
#> 3      B03 L26-001          S1 Fizzwell Chemicals     USA
#> 4      B04 L26-001          S1 Fizzwell Chemicals     USA
#> 5      B05 L26-002          S2 Plum Valley Supply  Canada

It’s handy for analysis, but terrible for storing data. “Fizzwell Chemicals, USA” is repeated on 16 rows, and that causes three kinds of trouble, called anomalies:

  • Update anomaly. If a supplier changes its name, you must change it on every row, and if you miss one, the table contradicts itself.
  • Insertion anomaly. You can’t record a new supplier until it has delivered a lot that was used in a batch.
  • Deletion anomaly. Delete the only batch that used a lot, and you lose everything you knew about that lot.

Normalization fixes this by splitting the data into tables where each fact lives in exactly one place. Database theory defines a ladder of normal forms. The first three cover almost everything:

Normal form Rule Broken by…
First (1NF) One value per cell, and no repeating groups of columns "98.9; 410; 5" in a single cell, or columns result1, result2, result3
Second (2NF) Every column depends on the whole key In a table keyed by batch + analyte, a reactor column, which depends on the batch alone
Third (3NF) Columns depend on the key, and on nothing else A supplier’s country in the batches table: it depends on the supplier, not the batch

The practical version fits in one sentence: each fact goes in the table of the thing it describes. A supplier’s country belongs in suppliers, a lot’s delivery date in lots, and a batch’s yield in batches.

You can recover the normalized tables from the flat one with distinct(), which keeps each unique combination once:

flat |> distinct(supplier_id, name, country)
#>   supplier_id               name country
#> 1          S1 Fizzwell Chemicals     USA
#> 2          S2 Plum Valley Supply  Canada
#> 3          S3 Rosewater Reagents     USA
#> 4          S4 Kestrel Industrial Germany

Notice the connection with Lesson 3: tidy data is really normalization applied to a single table. In practice you store normalized tables, and join them into a flat table whenever an analysis needs one. The flat table is a result, never the source.

distinct() takes the columns that describe a lot: lot_id, supplier_id, received, assay_pct.

flat |>

Data dictionaries

A table is only useful if people know what its columns mean. A data dictionary (or codebook) documents every column: its name, type and units, its allowed values, how missing values are coded, and where it came from. Here’s the start of one for the batches table:

Column Type Units Description
batch_id text Batch number, B01 to B40. Primary key.
reactor text R1 or R2
start_time date-time UTC When the reactor was charged
lot_id text Raw-material lot used. Foreign key to lots.
temp_C number °C Reactor temperature. NA when the sensor failed.
yield_pct number % Product made, as a percentage of the theoretical maximum

Some of a dictionary, like the types and the counts of missing values, can be computed, so you only have to write the descriptions by hand:

data.frame(column = names(batches),
           type = sapply(batches, class),
           missing = colSums(is.na(batches)),
           row.names = NULL) |>
  head(4)
#>       column      type missing
#> 1   batch_id character       0
#> 2    reactor character       0
#> 3 start_time character       0
#> 4   end_time character       0

data.frame(column = names(batches),

Design rules for statistical data

A few habits make data far easier to analyze later:

  1. Store raw measurements, not conclusions. Store the purity, and compute “on spec” from it. If the spec changes from 98.5% to 98.0%, you just rerun the code.
  2. One value per cell, with units in the column name or the dictionary. 98.9 in a column called purity_pct, not "98.9 %".
  3. One way to say “missing”. A real NA, not a mix of "n/a", -999 and blanks. (Lessons 11 and 12 show how much trouble the mix causes.)
  4. Dates and times in ISO format, with the time zone stated. The plant stores everything in UTC, and Lesson 10 shows why.
  5. IDs as text. Leading zeros matter, and nobody needs the average batch number.
  6. Write the dictionary as you go. You’ll never remember later what flag2 meant.

Challenge round

Challenge 1 · A key-checking function. Write is_key(df, cols), which returns TRUE if the columns cols together identify every row of df uniquely, and FALSE otherwise.

The columns are a key when the number of distinct combinations equals the number of rows. distinct(df, across(all_of(cols))) keeps one row per combination of the columns named in cols.

nrow(distinct(df, across(all_of(cols)))) == nrow(df)

is_key <- function(df, cols) {
  nrow(distinct(df, across(all_of(cols)))) == nrow(df)
}
c(is_key(lab, c("batch_id", "analyte")),
  is_key(lab, c("batch_id", "analyte", "measured_at")),
  is_key(batches, "lot_id"))

FALSE TRUE FALSE: batch + analyte isn’t a key (re-tests), adding the time makes one, and lot_id isn’t a key of batches, because each lot goes into several batches. all_of() lets you pass column names as text.

Challenge 2 · Spot an update anomaly. Someone edited a copy of the flat table by hand, and now one supplier appears under two different names. Find the supplier_id that has more than one name.

n_distinct(name) counts the different names within each supplier.

edited <- flat
edited$name[c(3, 25)] <- "Fizzwell Chemicals Inc."
edited |>
  group_by(supplier_id) |>
  summarise(n_names = n_distinct(name)) |>
  filter(n_names > 1)

Supplier S1 now has two names. In a normalized database, the name is stored once, in suppliers, so this can’t happen.

Quick quiz

1. In the relational model, what should each table describe?

Each table is one entity. Relationships between entities are stored as keys.

2. In an ERD, a line marked ||--o{ between SUPPLIERS and LOTS means…

|| means “exactly one” and o{ means “zero or more”: a one-to-many relationship.

3. A supplier changes its name, and you have to edit 16 rows of a table. What problem is that?

In a normalized design, the name lives in one row of suppliers, and changing it means changing one cell.

4. A cell contains "98.9; 410; 5" for purity, water and color. Which rule does that break?

Three values in one cell can’t be filtered, sorted or averaged without first splitting them apart.

5. Which of these should usually be computed rather than stored?

“On spec” is a conclusion drawn from the purity. If the spec changes, you just recompute it.

6. Why store lot numbers like 0042 as text?

IDs are labels, not quantities. Nobody needs the mean lot number, but everyone needs it to match.

Wrap-up

You can now design data, not just analyze it. Here’s what you’ve learned:

  • The relational model: one table per entity, rows as instances, columns as attributes, and keys for relationships.
  • ERDs picture a database’s tables and relationships. Crow’s feet show one-to-one, one-to-many and many-to-many.
  • Keys: natural or surrogate, single or composite. Always check they’re unique.
  • Normalization: each fact in the table of the thing it describes, which avoids update, insertion and deletion anomalies. Store normalized, join for analysis.
  • Data dictionaries document every column. Compute what you can, and write the rest as you go.

NoteKey words from this lesson
Relational model
Organizing data as tables of rows and columns, connected through keys.
Entity and attribute
An entity is a kind of thing a table describes. An attribute is one of its properties, stored as a column.
Entity-relationship diagram (ERD)
A diagram of a database’s tables, their columns and the relationships between them.
Natural, surrogate and composite keys
A natural key already has a meaning, a surrogate key is an ID made up for the purpose, and a composite key combines several columns.
Normalization
Splitting data into tables so that each fact is stored exactly once.
Normal forms (1NF, 2NF, 3NF)
Rules of increasing strictness: one value per cell, columns depending on the whole key, and on nothing but the key.
Anomaly
An inconsistency caused by storing a fact more than once: an update, insertion or deletion anomaly.
Data dictionary
A document describing every column of a dataset: its type, units, allowed values, missing codes and meaning.
