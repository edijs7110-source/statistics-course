Importing and exporting data

CSV, Excel, JSON, fixed-width, SAS, SPSS, Stata and Parquet files

Read and write the file formats that data really arrives in: delimited files with different locales and encodings, Excel workbooks, JSON, fixed-width text, SAS, SPSS and Stata files with labelled data, and Parquet.

Module 1 · Lesson 9 of 14 Week 24 of 160 About 5–7 hours

So far, your data has mostly arrived as tidy CSV files. Real data is rarely that polite. In the plant alone, the cooling-water contractor’s lab in Europe sends CSV files with commas for decimal points, the batch system exports Excel workbooks with a title on top, the online analyzer speaks JSON, the old chromatograph writes a fixed-width log, and the operator survey comes from SPSS. This lesson is a tour of the readers, and writers, for all of them.

Every file format is a little language. Once you know which questions to ask (What separates the values? Where does the header start? What does a decimal point look like?), almost any file will open.

In this lesson you’ll:

  • read delimited files with the right delimiter, decimal mark and column types
  • understand text encodings, and fix the classic “°C” mess
  • read Excel sheets, skipping titles and notes
  • turn nested JSON into a tidy table
  • read fixed-width files
  • read SAS, SPSS and Stata files, and handle their labels
  • export data, and know when to choose Parquet

Delimited files and locales

A delimited file is plain text, with one row per line and a special character between the values. CSV stands for comma-separated values, but in much of Europe the comma is the decimal mark, so files there put semicolons between the values instead. Here are the first lines of the cooling-water file:

readLines("data/cooling_water_eu.csv", n = 3, encoding = "latin1")
#> [1] "sample;date;temperature (°C);conductivity (µS/cm);pH"
#> [2] "CW-01;02.03.2026;21,7;805;7,82"                      
#> [3] "CW-02;03.03.2026;24,2;803;7,82"

Semicolons between the values, commas inside the numbers, and dates written day first. Read it with the wrong settings, and R does exactly what you asked, and the result is nonsense:

library(readr)
wrong <- read_delim("data/cooling_water_eu.csv", delim = ";",
                    locale = locale(encoding = "latin1"))
head(wrong, 3)
#> # A tibble: 3 × 5
#>   sample date       `temperature (°C)` `conductivity (µS/cm)`    pH
#>   <chr>  <chr>                   <dbl>                  <dbl> <dbl>
#> 1 CW-01  02.03.2026                217                    805   782
#> 2 CW-02  03.03.2026                242                    803   782
#> 3 CW-03  04.03.2026                232                    828   761

A pH of 782! readr took each comma for a thousands separator, as in 1,000, and quietly dropped it. No error and no warning, just wrong numbers. That’s why you should always look at your data, and check that the values are plausible, right after importing it.

The fix is a locale, readr’s name for a file’s local conventions. read_csv2() is the shortcut for semicolons with decimal commas, and locale() sets the rest:

cw <- read_csv2("data/cooling_water_eu.csv",
                locale = locale(encoding = "latin1", date_format = "%d.%m.%Y"))

date_format = "%d.%m.%Y" describes the dates: day, dot, month, dot, four-digit year. (Next lesson is all about dates.) A few other arguments are worth knowing:

  • col_types tells readr each column’s type, when you know better than its guess, for example col_types = cols(sample = col_character(), .default = col_double()).
  • na lists the strings that mean “missing”, for example na = c("", "NA", "n/a", "-").
  • spec(cw) shows the types that readr guessed, and problems(cw) lists any values that didn’t fit.

Your turn. Read the cooling-water file with read_delim(), and tell readr that the decimal mark is a comma. Then compute the mean pH.

The decimal mark is a comma, written as text: decimal_mark = ",".

cw <- read_delim("data/cooling_water_eu.csv", delim = ";",
                 locale = locale(encoding = "latin1", decimal_mark = ","))
mean(cw$pH)

A mean pH of 7.78, slightly alkaline, which is normal for cooling water.

Text encodings

Computers store text as numbers. An encoding is the table that says which number stands for which character. For plain English letters, nearly all encodings agree. The trouble starts with everything else: é, ü, °, µ, and every non-Latin alphabet.

Today almost everything uses UTF-8, which can store every character of every language. But older software, especially on European Windows computers, often writes Latin-1 (also called ISO-8859-1). In Latin-1, ° is the single byte B0. In UTF-8 it’s two bytes, C2 B0. So if you read a Latin-1 file as if it were UTF-8, the lone B0 makes no sense:

names(read_csv2("data/cooling_water_eu.csv", show_col_types = FALSE))
#> [1] "sample"                  "date"                   
#> [3] "temperature (\xb0C)"     "conductivity (\xb5S/cm)"
#> [5] "pH"

R shows the bytes it couldn’t decode, \xb0 and \xb5. (Without show_col_types = FALSE, readr would even stop with an “invalid multibyte string” error, because it can’t print the broken names in its summary of the columns.) The opposite mistake, reading UTF-8 as Latin-1, gives the famous mojibake: °C turns into Â°C. If you’ve ever seen that on a website, now you know why!

guess_encoding() makes an educated guess from the bytes, and then locale(encoding = ...) tells readr what to expect:

guess_encoding("data/cooling_water_eu.csv")
#> # A tibble: 2 × 2
#>   encoding   confidence
#>   <chr>           <dbl>
#> 1 ISO-8859-1       0.22
#> 2 ISO-8859-2       0.22

With only two special characters to go on, it’s a weak guess, but a good one. The golden rule of encodings: whatever comes in, write UTF-8 out. readr’s write_csv() always does.

Your turn. Read the file with the right encoding, and give the two awkward columns simple names, temp_C and cond_uS_cm. Column names with spaces and symbols need backticks.

The file is Latin-1: encoding = "latin1". With the wrong encoding, readr stops with an “invalid multibyte string” error, or rename() can’t find the columns, because their names don’t contain a real °.

read_csv2("data/cooling_water_eu.csv", locale = locale(encoding = "latin1")) |>
  rename(temp_C = `temperature (°C)`, cond_uS_cm = `conductivity (µS/cm)`) |>
  names()

Your turn. The workbook’s Notes sheet holds the operators’ comments on a few batches. Read both sheets, join them, and find the mean yield of the batches that have a note.

Skip the 3 rows above the header, and name the sheet in quotes: sheet = "Notes".

batches <- read_excel("data/batch_records.xlsx", sheet = "Batches", skip = 3)

JSON

Web services and instrument software often speak JSON (JavaScript Object Notation). Like CSV it’s plain text, but unlike a table it can nest: an object can hold lists, which can hold more objects. Here’s the start of the online analyzer’s export:

cat(readLines("data/analyzer_export.json", n = 16), sep = "\n")
#> {
#>   "instrument": {
#>     "id": "GC-ONLINE-2",
#>     "location": "Reactor R2 outlet",
#>     "software": "ChromaLog 3.1"
#>   },
#>   "runs": [
#>     {
#>       "run_id": 101,
#>       "time": "2026-03-10T07:30:00Z",
#>       "batch": "B18",
#>       "peaks": [
#>         {
#>           "compound": "solvent",
#>           "rt_min": 1.06,
#>           "area_pct": 2.54

Curly brackets { } hold named fields, and square brackets [ ] hold a list. The export describes the instrument, and then lists its runs. Each run has an ID, a time, a batch, and a list of peaks, one for each compound the chromatograph found. jsonlite’s fromJSON() turns it all into R lists and data frames:

Fixed-width files

Some older instruments and mainframe systems write fixed-width files. They have no delimiters at all: each column simply starts at the same position on every line. Here’s the start of the GC-1 chromatograph’s log:

cat(readLines("data/gc1_log.txt", n = 5), sep = "\n")
#> GC-1 RUN LOG  exported 2026-04-01
#> RUN  DATE    TIMESAMPLE  AREA%  RT
#> 00101202603021455B02-1     98.70  4.12
#> 00102202603022147B01-1     98.90  4.13
#> 00103202603031426B03-1     99.60  4.11

Without a description, that’s gibberish. The lab’s manual says that each line holds the run number (5 characters), the date (8), the time (4), the sample (8), the peak area in % (7) and the retention time in minutes (6). read_fwf() cuts each line at those widths, and skip = 2 skips the two header lines:

gc1 <- read_fwf("data/gc1_log.txt",
                col_positions = fwf_widths(c(5, 8, 4, 8, 7, 6),
                                           c("run", "date", "time", "sample", "area_pct", "rt")),
                col_types = cols(date = col_date("%Y%m%d"), time = col_character()),
                skip = 2)
gc1
#> # A tibble: 26 × 6
#>    run   date       time  sample area_pct    rt
#>    <chr> <date>     <chr> <chr>     <dbl> <dbl>
#>  1 00101 2026-03-02 1455  B02-1      98.7  4.12
#>  2 00102 2026-03-02 2147  B01-1      98.9  4.13
#>  3 00103 2026-03-03 1426  B03-1      99.6  4.11
#>  4 00104 2026-03-04 1813  B05-1      99.2  4.13
#>  5 00105 2026-03-06 0513  B07-1      99.2  4.13
#>  6 00106 2026-03-07 1607  B12-1      99.9  4.12
#>  7 00107 2026-03-08 0618  B11-1      99.1  4.12
#>  8 00108 2026-03-08 1257  B13-1      98.0  4.12
#>  9 00109 2026-03-09 0937  B14-1      99    4.13
#> 10 00110 2026-03-09 1803  B15-1      99.7  4.12
#> # ℹ 16 more rows

col_types reads the date as a real date, and keeps the time as text, so that 0513 doesn’t become the number 513. You can also give the columns as fwf_cols(run = 5, date = 8, ...), or by their start and end positions with fwf_positions().

Your turn. Some batches were tested twice on GC-1. Read the log, count the runs for each sample, and keep the samples with more than one run.

The widths are 5, 8, 4, 8, 7 and 6: c(5, 8, 4, 8, 7, 6).

read_fwf("data/gc1_log.txt",
         col_positions = fwf_widths(c(5, 8, 4, 8, 7, 6), c("run", "date", "time", "sample", "area_pct", "rt")),
         skip = 2, show_col_types = FALSE) |>
  count(sample) |>
  filter(n > 1)

SAS, SPSS and Stata files

Statistics has three classic commercial packages, each with its own file format, and the haven package reads and writes them all:

Software File Read with Write with
SAS .sas7bdat read_sas() use .xpt instead
SAS transport .xpt read_xpt() write_xpt()

Stata .dta read_dta() write_dta()

Here’s the batch table as a Stata file, and as a SAS transport file. The US Food and Drug Administration requires transport files for clinical trial data, so they’re everywhere in the pharmaceutical industry.

<dbl+lbl> marks a labelled column: numbers, with names attached. Before analyzing, you usually want a factor instead, and as_factor() makes one from the labels:

count(survey, role = as_factor(role))
#> # A tibble: 3 × 2
#>   role           n
#>   <fct>      <int>
#> 1 operator      24
#> 2 technician    15
#> 3 engineer       9

zap_labels() does the opposite: it drops the labels and keeps the bare numbers.

SPSS also lets you declare certain codes to be missing, like 9 = “no answer”. By default, read_sav() turns those user-defined missing values into NA, which is safe. But if you keep them with user_na = TRUE, and then convert carelessly, the 9s sneak into your numbers:

survey_9 <- read_sav("data/operator_survey.sav", user_na = TRUE)
mean(survey$workload, na.rm = TRUE)    # "no answer" is NA: correct
#> [1] 2.977778
mean(as.numeric(survey_9$workload))    # "no answer" counts as a 9: wrong!
#> [1] 3.354167

Three “no answer”s, counted as scores of 9, push the mean workload from 2.98 to 3.35. Always look at a variable’s labels before you compute with it!

Your turn. Compute the mean overtime for each role, with the roles’ names rather than their codes.

as_factor(role) turns the codes 1, 2 and 3 into the labels operator, technician and engineer.

read_sav("data/operator_survey.sav") |>
  mutate(role = as_factor(role)) |>
  group_by(role) |>
  summarise(n = n(), mean_overtime = mean(overtime_h))

The technicians worked the most overtime: almost 9 hours last month, on average.

Exporting, and Parquet

Every reader has a writer: write_csv(), write_xlsx() from writexl, write_json(), and haven’s write_sav(), write_dta() and write_xpt(). So which format should you choose? That depends on who, or what, is going to read the file.

CSV can be read by everything, and will be forever, but it only stores text. Every column’s type has to be guessed again when the file is read back, and some types can’t be recovered at all:

test <- tibble(
  id = 1:3,
  grade = factor(c("low", "high", "low"), levels = c("low", "high")),
  time = as.POSIXct("2026-03-02 06:00", tz = "UTC") + 3600 * 0:2
)
write_csv(test, "test.csv")
read_csv("test.csv", show_col_types = FALSE)
#> # A tibble: 3 × 3
#>      id grade time               
#>   <dbl> <chr> <dttm>             
#> 1     1 low   2026-03-02 06:00:00
#> 2     2 high  2026-03-02 07:00:00
#> 3     3 low   2026-03-02 08:00:00

The whole numbers came back as decimals (dbl instead of int), and the factor came back as plain text, with its level order lost.

Parquet is a modern file format, designed for data analysis. It stores each column’s type, it’s compressed, and it’s fast to read. Python, R, Spark, DuckDB and Arrow all understand it. The small nanoparquet package reads and writes it:

library(nanoparquet)
write_parquet(test, "test.parquet")
read_parquet("test.parquet")
#> # A data frame: 3 × 3
#>      id grade time               
#>   <int> <fct> <dttm>             
#> 1     1 low   2026-03-02 06:00:00
#> 2     2 high  2026-03-02 07:00:00
#> 3     3 low   2026-03-02 08:00:00
file.size(c("data/sensor_log.csv", "data/sensor_log.parquet"))
#> [1] 12142  4627

Every type survived. And as Parquet, the sensor log takes up less than half the space it does as CSV. For files that only R will ever read, saveRDS() and readRDS() store any R object exactly, but no other software can open them.

CSV sharing with anyone, forever no
Excel (.xlsx) people who’ll open it in Excel partly

Your turn. A colleague wants the batches and the notes in one Excel file, with a sheet for each. write_xlsx() makes one sheet for each data frame in a named list.

The names in the list become the sheet names: list(batches = batches, notes = notes).

batches <- read_excel("data/batch_records.xlsx", sheet = "Batches", skip = 3)
notes <- read_excel("data/batch_records.xlsx", sheet = "Notes")
writexl::write_xlsx(list(batches = batches, notes = notes), "plant_export.xlsx")
excel_sheets("plant_export.xlsx")

Reading your own export back is a good habit: it proves that the file really contains what you think it does.

Challenge round

Challenge 1 · The hottest day. Read the cooling-water file properly, with real numbers and real dates, and find the date of the highest water temperature.

You need three settings: semicolons with decimal commas (read_csv2()), the encoding, and the date format.

read_csv2("data/cooling_water_eu.csv", locale = locale(encoding = "latin1", date_format = "%d.%m.%Y"))

cw <- read_csv2("data/cooling_water_eu.csv",
                locale = locale(encoding = "latin1", date_format = "%d.%m.%Y"))
cw$date[which.max(cw$`temperature (°C)`)]

21 March 2026, the last day of the campaign, at 27.6 °C.

Challenge 2 · Workload by shift. Compute the mean workload score on each shift, with the shifts’ names. Make sure that “no answer” doesn’t count as a score! Also count how many people on each shift actually answered.

With the default settings, “no answer” is already NA. Turn shift into a factor, group by it, and use na.rm = TRUE. sum(!is.na(workload)) counts the answers.

mutate(shift = as_factor(shift)) |>
  group_by(shift) |>
  summarise(answered = sum(!is.na(workload)), mean_workload = mean(workload, na.rm = TRUE))
read_sav("data/operator_survey.sav") |>
  mutate(shift = as_factor(shift)) |>
  group_by(shift) |>
  summarise(answered = sum(!is.na(workload)), mean_workload = mean(workload, na.rm = TRUE))

All three “no answer”s came from the day shift, where 23 of 26 people answered. The two shifts rate their workload about the same, just below 3, “about right”.

Quick quiz

1. A European CSV file shows 7,82 in its pH column. What does read_csv2() assume?

That’s the usual convention wherever the comma is the decimal mark. For anything else, use read_delim() with a locale().

2. A web page shows Â°C where it should say °C. What went wrong?

In UTF-8, ° is the two bytes C2 B0. Read as Latin-1, each byte becomes its own character: C2 is Â, and B0 is °.

3. An Excel sheet has a title in row 1, a note in row 2, an empty row 3, and the column names in row 4. How do you read it?

skip = 3 skips the first three rows, so that row 4 is read as the header.

4. After fromJSON(), a column holds a small data frame in every cell. What does unnest() do with it?

Nine runs, each with three peaks, become 27 rows, one for each peak.

5. An SPSS column has the codes 1, 2 and 3, labelled operator, technician and engineer. What does as_factor() give you?

as_factor() uses the value labels. zap_labels() would give you the bare numbers instead.

6. You’re sharing a large dataset with a colleague who works in Python. Why might you choose Parquet over CSV?

Both formats work in Python. But Parquet saves your colleague from guessing the types, and it’s much faster for big files.

Wrap-up

Data can arrive in any shape now, and you’ll get it in! Here’s what you’ve learned:

  • Delimited files: read_csv(), read_csv2() and read_delim(), with a locale() for the decimal mark, encoding and date format. Always check that the values are plausible after importing.
  • Encodings: UTF-8 can store everything, while older files are often Latin-1. Mismatches show up as \xb0 or as mojibake like Â°C. Write UTF-8 out.
  • Excel: excel_sheets(), then read_excel() with sheet, skip and range. write_xlsx() writes one sheet for each data frame in a named list.
  • JSON: fromJSON() makes lists and data frames, and unnest() flattens list-columns.
  • Fixed-width: read_fwf() with fwf_widths(), plus a description of the columns.
  • SAS, SPSS and Stata: haven’s read_sas(), read_xpt(), read_sav() and read_dta(). Use as_factor() for value labels, and watch out for user-defined missing codes.
  • Choosing a format: CSV for anyone, Parquet for types and speed, .rds for R alone.

NoteKey words from this lesson
Delimiter
The character that separates the values in a text file, like a comma, semicolon or tab.
Locale
A file’s local conventions: its decimal mark, grouping mark, encoding and date format.
Encoding
The table that maps bytes to characters. UTF-8 is the modern standard, and Latin-1 is a common older one.
Mojibake
Garbled text, like Â°C, caused by reading text with the wrong encoding.
List-column
A data frame column whose cells hold whole lists or data frames, often the result of reading JSON.
Fixed-width file
A text file in which every column starts at the same position on every line.
Value label and variable label
In SPSS and Stata, a name for a code (1 = “operator”), and a description of a whole column.
User-defined missing value
A code, like 9 = “no answer”, that SPSS treats as missing.
Parquet
A compressed, column-based file format that stores each column’s type.
