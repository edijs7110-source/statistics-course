Data quality and validation

Finding errors, duplicates and outliers, and writing down what you did

Clean column names, turn messy text into numbers, find duplicates, check data against validation rules, judge outliers, handle values below a detection limit, and document every cleaning decision.

Module 1 · Lesson 11 of 14 Week 26 of 160 About 5–7 hours

Last lesson, you fixed how things were written: batch codes, test names and times. This lesson asks a harder question: is the data right? Are there results typed in twice? Values that can’t be true? Numbers hiding inside text? By the end, you’ll have turned the lab’s messy spreadsheet into a table that you can trust, and you’ll be able to say exactly what you changed, and why.

A good data cleaner is part detective and part lab technician: suspicious of everything, and careful to write it all down. Magnifying glass at the ready!

In this lesson you’ll:

  • clean up column names automatically with janitor
  • turn messy text into numbers, without being fooled
  • handle values below a detection limit
  • tell duplicates apart from genuine repeats
  • check data against validation rules
  • decide whether an outlier is an error or a discovery
  • document your cleaning decisions, and test them with assertions

Clean names

Lesson 1 promised a function that tidies messy column names. It’s clean_names(), from the janitor package. It makes every name lower case, replaces spaces and symbols with underscores, and spells out % and #:

library(janitor)
#> 
#> Attaching package: 'janitor'
#> The following objects are masked from 'package:stats':
#> 
#>     chisq.test, fisher.test
messy <- tibble(`Batch ID` = 1, `Temp (°C)` = 2, `Yield %` = 3, pressureBar = 4, `Batch ID ` = 5)
names(clean_names(messy))
#> [1] "batch_id"      "temp_c"        "yield_percent" "pressure_bar" 
#> [5] "batch_id_2"

Notice that pressureBar became pressure_bar, and the second Batch ID became batch_id_2, so that the names stay unique. Automatic cleaning is a great start, but always look at the result. Here are the cooling-water names from Lesson 9:

cw <- read_csv2("data/cooling_water_eu.csv", locale = locale(encoding = "latin1"), show_col_types = FALSE)
names(clean_names(cw))
#> [1] "sample"              "date"                "temperature_c"      
#> [4] "conductivity_m_s_cm" "p_h"

The µ became an m (so microsiemens now look like millisiemens, a thousand times bigger!), and pH was split into p_h. janitor even warns you about the µ. A quick rename() fixes both.

Your turn. Clean the cooling-water names, then rename the two that went wrong: call them conductivity_uS_cm and ph.

rename() takes new_name = old_name. The old names are the ones clean_names() produced: conductivity_m_s_cm and p_h.

read_csv2("data/cooling_water_eu.csv", locale = locale(encoding = "latin1"), show_col_types = FALSE) |>
  clean_names() |>
  rename(conductivity_uS_cm = conductivity_m_s_cm, ph = p_h) |>
  names()

Numbers hiding in text

Here’s last lesson’s work on the raw lab file, in one step: clean batch codes, analytes and times. The value column is still text, though, because not every value is a number:

raw <- read_csv("data/lab_results_raw.csv", col_types = cols(.default = col_character()))
lab_raw <- raw |>
  mutate(batch_id = str_c("B", str_pad(str_extract(batch, "\\d+"), 2, pad = "0")),
         analyte = case_when(str_detect(test, regex("pur", ignore_case = TRUE)) ~ "purity",
                             str_detect(test, regex("water|h2o", ignore_case = TRUE)) ~ "water",
                             str_detect(test, regex("colou?r|apha", ignore_case = TRUE)) ~ "color"),
         measured_at = parse_date_time(measured, orders = c("Ymd HM", "dmY HM", "bdY IMp"), tz = "UTC")) |>
  select(batch_id, analyte, measured_at, value, instrument, analyst)

lab_raw |>
  filter(is.na(suppressWarnings(as.numeric(value)))) |>
  count(value, sort = TRUE)
#> # A tibble: 23 × 2
#>    value       n
#>    <chr>   <int>
#>  1 154 ppm     3
#>  2 99,9        2
#>  3 <20         2
#>  4 n/a         2
#>  5 -           1
#>  6 174 ppm     1
#>  7 201 ppm     1
#>  8 202 ppm     1
#>  9 217 ppm     1
#> 10 221 ppm     1
#> # ℹ 13 more rows

as.numeric() turns anything that isn’t a plain number into NA, so this lists every troublemaker: units typed into the cell (154 ppm), decimal commas (99,9), values below the detection limit (<20), and three different ways of saying “missing” (n/a, - and a blank cell, which readr has already made NA).

readr’s parse_number() looks like the perfect tool, because it ignores any text around a number. But watch what it does with the tricky ones:

parse_number(c("154 ppm", "98,83", "<20", "n/a"))
#> Warning: 1 parsing failure.
#> row col expected actual
#>   4  -- a number    n/a
#> [1]  154 9883   20   NA
#> attr(,"problems")
#> # A tibble: 1 × 4
#>     row   col expected actual
#>   <int> <int> <chr>    <chr> 
#> 1     4    NA a number n/a

154 ppm is fine. But 98,83 became 9,883, because the comma was taken for a thousands separator, just like the pH of 782 in Lesson 9. <20 became 20, which is wrong: it means less than 20. And n/a gave a parsing failure. Each one needs handling on purpose: replace the commas first, tell parse_number() which strings mean missing, and keep a note of the values that were below the detection limit.

Values below the detection limit. The lab’s water titrator can’t measure below 20 ppm, so it reports <20. The true value is somewhere between 0 and 20. That’s a censored value: you know a range, not a number. Turning it into NA throws away real information (we know the water was low), and using 20 overstates it. A common convention, and the one the plant’s database uses, is half the limit: 10 ppm. Whichever you choose, keep a below_lod column, so that the choice can be revisited, and say what you did in your report.

Your turn. Parse the values. Replace each decimal comma with a point first, then count the missing values, and find the highest purity.

Replace a comma with a point: str_replace(value, ",", ".").

lab_raw |>
  mutate(value = parse_number(str_replace(value, ",", "."), na = c("", "NA", "n/a", "-"))) |>
  summarise(missing = sum(is.na(value)),
            max_purity = max(value[analyte == "purity"], na.rm = TRUE))

Four missing values, and a highest purity of 101.2%. A purity above 100% is impossible, so that’s a problem for the next steps.

Duplicates and repeats

A duplicate is the same observation recorded twice, usually by accident. janitor’s get_dupes() shows the rows that share the same values in the columns you name:

get_dupes(lab_raw, batch_id, analyte, measured_at)
#> # A tibble: 6 × 7
#>   batch_id analyte measured_at         dupe_count value instrument analyst
#>   <chr>    <chr>   <dttm>                   <int> <chr> <chr>      <chr>  
#> 1 B02      color   2026-03-02 15:20:00          2 13    COL-1      A1     
#> 2 B02      color   2026-03-02 15:20:00          2 13    COL-1      A1     
#> 3 B30      purity  2026-03-17 04:22:00          2 101.2 GC-1       A2     
#> 4 B30      purity  2026-03-17 04:22:00          2 101.2 GC-1       A2     
#> 5 B32      water   2026-03-18 03:25:00          2 330   KF-1       A3     
#> 6 B32      water   2026-03-18 03:25:00          2 330   KF-1       A3

Three results were typed in twice. But be careful: not every repeated batch and analyte is a mistake. Six batches had their purity re-tested, and those are genuine, separate measurements, taken at different times:

lab_raw |>
  distinct(batch_id, analyte, measured_at) |>
  count(batch_id, analyte) |>
  filter(n > 1)
#> # A tibble: 6 × 3
#>   batch_id analyte     n
#>   <chr>    <chr>   <int>
#> 1 B19      purity      2
#> 2 B21      purity      2
#> 3 B25      purity      2
#> 4 B34      purity      2
#> 5 B35      purity      2
#> 6 B39      purity      2

That’s why the key matters. A result is identified by its batch, its analyte and its time, as you saw in Lesson 6. Two rows that agree on all three are duplicates. Two rows that differ only in time are a re-test, and both belong in the data.

One more trap: duplicates can hide behind messy spellings. B2 and B02 aren’t duplicates as text, but they’re the same batch. Always look for duplicates after standardizing the keys, as you just did.

Your turn. Remove the duplicates, keeping one row for each batch, analyte and time. How many rows are left?

List the three key columns: batch_id, analyte, measured_at. .keep_all = TRUE keeps the other columns too.

lab_raw |>
  distinct(batch_id, analyte, measured_at, .keep_all = TRUE) |>
  nrow()

124 rows, exactly as many as the lab’s database holds.

Validation rules

You can write down what “correct” means as a list of validation rules, and then check the data against all of them at once. That’s what the validate package is for. First, here’s the parsed, de-duplicated table:

lab <- lab_raw |>
  mutate(below_lod = str_detect(value, "^<") %in% TRUE,
         value = parse_number(str_replace(value, ",", "."), na = c("", "NA", "n/a", "-"))) |>
  distinct(batch_id, analyte, measured_at, .keep_all = TRUE)

validator() holds the rules, each one a condition that should be true for every row, and confront() checks the data against them:

library(validate)
rules <- validator(
  code_ok = grepl("^B[0-9]{2}$", batch_id),
  not_missing = !is.na(value),
  purity_max = if (analyte == "purity") value <= 100
)
out <- confront(lab, rules)
summary(out)[, 1:5]
#>          name items passes fails nNA
#> 1     code_ok   124    124     0   0
#> 2 not_missing   124    120     4   0
#> 3  purity_max   124    121     1   2

Every batch code is fine, four values are missing, and one purity is above 100%. (nNA counts the rows that couldn’t be checked: the two missing purities.) violating() pulls out the rows that broke a rule:

violating(lab, out["purity_max"])
#> # A tibble: 1 × 7
#>   batch_id analyte measured_at         value instrument analyst below_lod
#>   <chr>    <chr>   <dttm>              <dbl> <chr>      <chr>   <lgl>    
#> 1 B30      purity  2026-03-17 04:22:00  101. GC-1       A2      FALSE

Some rules span two tables. Every lab result must belong to a real batch, so this should return nothing:

batches <- read_csv("data/batches.csv", show_col_types = FALSE)
anti_join(lab, batches, by = "batch_id")
#> # A tibble: 0 × 7
#> # ℹ 7 variables: batch_id <chr>, analyte <chr>, measured_at <dttm>,
#> #   value <dbl>, instrument <chr>, analyst <chr>, below_lod <lgl>

It doesn’t, which means that the batch codes were cleaned well. Remember B5 and B41, the orphans from Lesson 5? This is the check that catches them, before they’re loaded. A quick cross-table, with janitor’s tabyl(), checks something else that should hold: each analyte comes from the right instruments.

tabyl(lab, analyte, instrument)
#>  analyte COL-1 GC-1 GC-2 KF-1
#>    color    40    0    0    0
#>   purity     0   26   20    0
#>    water     0    0    0   38

Your turn. Add a rule that water contents can’t be negative, and find the row that breaks it.

Follow the pattern of the purity rule: if (analyte == "water") value >= 0.

rules <- validator(
  purity_max = if (analyte == "purity") value <= 100,
  water_min = if (analyte == "water") value >= 0
)
out <- confront(lab, rules)
violating(lab, out["water_min"])

B25’s water content is −15 ppm. Most likely, someone typed a minus sign by mistake.

Outliers: errors or discoveries?

An outlier is a value far from the rest. It might be an error, or it might be the most interesting thing in your data! There are three common ways to flag them:

  • Range checks use what’s physically possible. The reactors can’t reach 999.9 °C, so the sensor log’s reading from Lesson 3 is a glitch:
sensor <- read_csv("data/sensor_log.csv", show_col_types = FALSE)
sensor$R1_temp_C[sensor$R1_temp_C > 300]
#> [1] 999.9
  • The IQR rule flags values more than 1.5 interquartile ranges below the first quartile, or above the third. It’s the rule that a boxplot uses to draw its separate points, and boxplot.stats(x)$out lists them.
  • Z-scores, the distance from the mean in standard deviations, flag values beyond 3 or so. But a big outlier inflates the standard deviation itself, so it can hide behind its own z-score. The IQR rule is more robust.

A flag is a question, not a verdict. Before you change or delete anything, look at the context.

Your turn. Flag the water results outside the IQR fences.

The upper fence is the third quartile plus the fence: q[2] + fence.

water <- lab |> filter(analyte == "water", !is.na(value))
q <- quantile(water$value, c(0.25, 0.75))
fence <- 1.5 * (q[2] - q[1])
water |>
  filter(value < q[1] - fence | value > q[2] + fence) |>
  select(batch_id, value, below_lod)

Six flags, but look closer. B18, B19 and B32 used Kestrel’s wet lots (Lesson 5), so their high water is real, and it’s the most important finding in the whole dataset! B16 and B28 are the two results below the detection limit: real, just low. Only B25’s −15 ppm is an error. Deleting all six “outliers” would have thrown away the discovery.

Writing it all down

Every cleaning step is a decision, and decisions should be written down. Three habits make cleaning trustworthy:

  1. Never edit the raw data. It stays in data-raw/, exactly as you received it. Every change happens in a script, so it can be re-run, and checked, by anyone.
  2. Keep a cleaning log. List each decision, the reason for it, and how many rows it touched. It’s a small table, and it answers the questions that every reviewer asks.
  3. End with assertions. An assertion is a check that stops the script, loudly, if the data breaks a rule. stopifnot() takes conditions, each with a message:
cleaning_log <- tribble(
  ~decision,                                     ~reason,                          ~rows,
  "Standardized the batch codes to B01-B40",     "82 spellings of 40 codes",       127,
  "Read decimal commas as decimal points",       "European number format",          10,
  "Removed units typed into the cells",          "values must be numbers",          12,
  "Recoded n/a, - and blanks as missing",        "three ways of saying missing",     4,
  "Set <20 ppm to 10 ppm, flagged in below_lod", "half the detection limit",         2,
  "Removed rows that were typed in twice",       "exact duplicates",                 3,
  "Set purity 101.2% and water -15 ppm to NA",   "physically impossible",            2
)
cleaning_log
#> # A tibble: 7 × 3
#>   decision                                    reason                        rows
#>   <chr>                                       <chr>                        <dbl>
#> 1 Standardized the batch codes to B01-B40     82 spellings of 40 codes       127
#> 2 Read decimal commas as decimal points       European number format          10
#> 3 Removed units typed into the cells          values must be numbers          12
#> 4 Recoded n/a, - and blanks as missing        three ways of saying missing     4
#> 5 Set <20 ppm to 10 ppm, flagged in below_lod half the detection limit         2
#> 6 Removed rows that were typed in twice       exact duplicates                 3
#> 7 Set purity 101.2% and water -15 ppm to NA   physically impossible            2
stopifnot(
  "one row per result" = !anyDuplicated(lab[c("batch_id", "analyte", "measured_at")]),
  "purity can't exceed 100%" = all(lab$value[lab$analyte == "purity"] <= 100, na.rm = TRUE)
)
#> Error:
#> ! purity can't exceed 100%

The first condition holds, but the second doesn’t, so the script stops right there, before the impossible purity can sneak into an analysis. Once the impossible values are dealt with, the same lines pass in silence.

One last trap, for when you compare your cleaned values with another source. Decimal numbers are stored in binary, so two ways of computing “the same” number can differ in the 15th decimal place. For example, parse_number() and as.numeric() don’t always agree exactly. So never compare decimals with ==. Use dplyr’s near() instead, which allows for a tiny tolerance:

0.1 + 0.2 == 0.3
#> [1] FALSE
near(0.1 + 0.2, 0.3)
#> [1] TRUE

Challenge round

Challenge 1 · A spike detector. A sensor glitch is a spike: a single reading far from both of its neighbors. Find the R1 temperatures that differ by more than 100 °C from the reading before them and from the reading after them.

lead() is the reading after. Compare with it the same way as with lag().

sensor |>
  filter(abs(R1_temp_C - lag(R1_temp_C)) > 100,
         abs(R1_temp_C - lead(R1_temp_C)) > 100) |>
  select(timestamp, R1_temp_C)

Exactly one spike: the 999.9 °C at 03:15. Why 100 °C? In 5 minutes, a real reactor temperature rises by about 30 °C while heating up, and falls by up to 50 °C while cooling down after a batch, but it never changes by 100.

Challenge 2 · From raw to right. Finish the cleaning: flag the values below the detection limit, parse the values, remove the duplicates, and deal with the impossible and censored values. Then compare your table with the lab’s database, official. How many of your 124 values agree with it?

below_lod is TRUE when the text value starts with <: str_detect(value, "^<"). It has to be computed before value is turned into a number.

The plant’s convention for <20 is half the detection limit: below_lod ~ 10.

final <- lab_raw |>
  mutate(below_lod = str_detect(value, "^<"),
         value = parse_number(str_replace(value, ",", "."), na = c("", "NA", "n/a", "-"))) |>
  distinct(batch_id, analyte, measured_at, .keep_all = TRUE) |>
  mutate(value = case_when(
    analyte == "purity" & value > 100 ~ NA,
    analyte == "water" & value < 0 ~ NA,
    below_lod ~ 10,
    .default = value
  ))
final |>
  inner_join(official, by = c("batch_id", "analyte", "measured_at"), suffix = c("", "_db")) |>
  summarise(rows = n(), agree = sum(near(value, value_db), na.rm = TRUE))

118 of the 124 values agree. The other six are the four missing values and the two impossible ones, which the spreadsheet simply doesn’t have. The lab’s database has all six, straight from the instruments. That’s the best fix of all: when you can, go back to the source.

Quick quiz

1. What does clean_names() turn the column name Yield % into?

It makes names lower case, joins words with underscores, and spells out % as “percent”.

2. What does parse_number("98,83") return?

With the default locale, the comma is a thousands separator, so it’s dropped. Replace decimal commas with points first, or set the locale’s decimal_mark.

3. A water result is recorded as <20. What do you know about the true value?

It’s a censored value. Keep a flag for it, and document how you handled it, for example by using half the detection limit.

4. Batch B19 has two purity results, measured at different times. What are they?

Duplicates agree on the whole key, including the time. Results at different times are separate measurements.

5. The IQR rule flags B18’s water content of 410 ppm. What should you do?

A flag is a question, not a verdict. Here, the “outlier” is the most important finding in the data.

6. Why end a cleaning script with stopifnot() assertions?

Assertions turn silent problems into loud ones, every time the script runs, even when new data arrives.

Wrap-up

You can turn a messy spreadsheet into data you trust! Here’s what you’ve learned:

  • Names: clean_names() from janitor, followed by a careful look and a rename() where needed.
  • Values: find the non-numbers with as.numeric(), and parse them with care: decimal commas first, missing codes in na, and censored values flagged.
  • Detection limits: a value like <20 is censored. Keep a flag, choose a convention such as half the limit, and document it.
  • Duplicates: get_dupes() and distinct() on the full key, after standardizing it. Re-tests aren’t duplicates.
  • Rules: validator(), confront(), summary() and violating(), plus anti_join() checks across tables.
  • Outliers: range checks, the IQR rule and z-scores flag values. Context decides whether they’re errors.
  • Documentation: raw data stays read-only, a cleaning log records each decision, and stopifnot() assertions guard the result. Compare decimals with near(), not ==.

NoteKey words from this lesson
Validation rule
A condition that every row of correct data should meet, like “purity is at most 100%”.
Duplicate
The same observation recorded more than once, usually by accident.
Re-test
A genuine second measurement of the same thing, at a different time. Not a duplicate.
Detection limit and censored value
The smallest amount an instrument can measure, and a value known only to lie beyond such a limit, like <20.
Outlier
A value far from the rest of the data. It may be an error, or a real and important result.
IQR rule
Flags values more than 1.5 interquartile ranges beyond the quartiles, as a boxplot does.
Referential integrity
Every foreign key value has a matching row in the table it points to.
Cleaning log
A record of each cleaning decision, its reason, and the number of rows it touched.
Assertion
A check that stops a script with an error if the data breaks a rule.
