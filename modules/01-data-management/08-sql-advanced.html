Joins, subqueries, CTEs, window functions, and dplyr that writes SQL for you

Join tables in SQL, build queries in steps with subqueries and common table expressions, rank and accumulate with window functions, create tables and indexes, and let dbplyr translate dplyr code into SQL.

But the interesting questions in the plant span several of them: which supplier’s lots make the wettest product? needs the lab results, the batches, the lots and the suppliers, all at once. Joins in SQL

A join in SQL names both tables, and says how their rows match with ON:

dbGetQuery(con, "
  SELECT b.batch_id, b.reactor, o.name, o.shift
  FROM batches AS b
  INNER JOIN operators AS o ON b.operator_id = o.operator_id
  LIMIT 4
")
#>   batch_id reactor  name shift
#> 1      B01      R1 Priya   day
#> 2      B02      R2  Maya   day
#> 3      B03      R1 Jonas   day
#> 4      B04      R2   Tom night

b and o are table aliases: short nicknames, given with AS. b.batch_id means “the batch_id column of b”. You need the prefix whenever both tables have a column with the same name, like operator_id, and it makes long queries easier to read anyway.

The SQL joins match the dplyr ones from Lesson 5:

SQL dplyr Keeps
INNER JOIN, or just JOIN inner_join() only the rows with a match in both tables
LEFT JOIN left_join() every row of the left table, matched or not
FULL JOIN full_join() every row of both tables

Once the tables are joined, everything from last lesson works on the combined rows. Here’s the mean yield on each shift:

dbGetQuery(con, "
  SELECT o.shift, COUNT(*) AS n, AVG(b.yield_pct) AS mean_yield
  FROM batches AS b
  INNER JOIN operators AS o ON b.operator_id = o.operator_id
  GROUP BY o.shift
")
#>   shift  n mean_yield
#> 1   day 22   56.72273
#> 2 night 18   58.77778

Your turn. Last lesson you found that OP1 and OP5 ran more than 8 batches each. Now put names to them: join operators to batches, and count the batches for each operator’s name.

The two tables share the column operator_id. Match it with b.operator_id = o.operator_id.

dbGetQuery(con, "
  SELECT o.name, COUNT(*) AS n
  FROM batches AS b
  INNER JOIN operators AS o ON b.operator_id = o.operator_id
  GROUP BY o.name
  HAVING COUNT(*) > 8
")

Maya ran 11 batches and Lena ran 9.

A LEFT JOIN keeps every row of the left table, and fills in NULL where there’s no match. That makes it the tool for finding what’s missing: join, then keep the rows where the right-hand side is NULL.

Your turn. Find the batches that have no water result.

A batch with no water result has nothing to match, so all of its l columns are NULL. Keep the rows where l.result_id IS NULL.

dbGetQuery(con, "
  SELECT b.batch_id
  FROM batches AS b
  LEFT JOIN lab_results AS l
    ON b.batch_id = l.batch_id AND l.analyte = 'water'
  WHERE l.result_id IS NULL
")

B12 and B33, the two batches whose water test was never run.

Notice that l.analyte = 'water' sits in the ON clause, as part of the matching rule. In WHERE, it would run after the join and throw away the unmatched rows, whose analyte is NULL. Those are exactly the rows you’re looking for, so you’d get nothing back!

Subqueries

A subquery is a query inside another query, in brackets. The inner query runs first, and the outer one uses its answer. How many batches beat the average yield?

dbGetQuery(con, "
  SELECT COUNT(*) AS n
  FROM batches
  WHERE yield_pct > (SELECT AVG(yield_pct) FROM batches)
")
#>    n
#> 1 19

You can’t write WHERE yield_pct > AVG(yield_pct), because WHERE looks at one row at a time, and an average needs all of them. The subquery works out the average first.

A subquery can also return a whole list of values, for use with IN. Which batches used one of Kestrel Industrial’s lots?

dbGetQuery(con, "
  SELECT batch_id, lot_id, yield_pct
  FROM batches
  WHERE lot_id IN (SELECT lot_id FROM lots WHERE supplier_id = 'S4')
")
#>   batch_id  lot_id yield_pct
#> 1      B18 L26-006      48.9
#> 2      B19 L26-006      58.4
#> 3      B20 L26-006      65.2
#> 4      B31 L26-010      56.7
#> 5      B32 L26-010      56.3
#> 6      B33 L26-010      69.5
#> 7      B34 L26-010      56.0

IN (subquery) is SQL’s semi join, and NOT IN (subquery) is its anti join. Be careful with NOT IN, though: if the subquery’s list contains a NULL, nothing matches at all. The LEFT JOIN with IS NULL from the last step is the safer anti join.

Your turn. Six batches had their purity re-tested. Use a subquery on lab_results to list them.

Inside the brackets, write a whole query that returns the batch_id of every re-test: SELECT batch_id FROM lab_results WHERE retest = 1.

dbGetQuery(con, "
  SELECT batch_id, catalyst, yield_pct
  FROM batches
  WHERE batch_id IN (SELECT batch_id FROM lab_results WHERE retest = 1)
")

Common table expressions

Subqueries inside subqueries soon become hard to read. A common table expression (CTE) gives a query a name, with WITH, at the very top. After that, you can use it just like a table:

dbGetQuery(con, "
  WITH purity AS (
    SELECT batch_id, value AS purity
    FROM lab_results
    WHERE analyte = 'purity' AND retest = 0
  )
  SELECT b.catalyst, COUNT(*) AS n, AVG(p.purity) AS mean_purity
  FROM batches AS b
  INNER JOIN purity AS p ON b.batch_id = p.batch_id
  GROUP BY b.catalyst
")
#>   catalyst  n mean_purity
#> 1        A 10    98.79400
#> 2        B 12    98.90917
#> 3        C  9    98.97000
#> 4        D  9    98.96667

Read it from top to bottom, like a pipe: first make purity, then join it to batches and summarize. CTEs are the closest thing SQL has to |>. You can define several, separated by commas, as in WITH a AS (...), b AS (...) SELECT ..., and each one can use the ones before it.

One more trick that you’ll often see inside CTEs: CASE WHEN ... THEN ... END is SQL’s case_when(). Combined with GROUP BY, it can even do the job of pivot_wider():

dbGetQuery(con, "
  SELECT batch_id,
    MAX(CASE WHEN analyte = 'purity' THEN value END) AS purity,
    MAX(CASE WHEN analyte = 'water' THEN value END) AS water,
    MAX(CASE WHEN analyte = 'color' THEN value END) AS color
  FROM lab_results
  WHERE retest = 0
  GROUP BY batch_id
  LIMIT 4
")
#>   batch_id purity water color
#> 1      B01  98.90   184    21
#> 2      B02  98.70   154    13
#> 3      B03  99.60   221    15
#> 4      B04  98.83   219    21

For each batch, the CASE picks out the value of one analyte, and MAX() collapses the group to that single value.

Your turn. Complete the CTE water, so that it holds the water results. The rest of the query then finds the mean water content for each catalyst.

Keep only the water results: analyte = 'water'.

dbGetQuery(con, "
  WITH water AS (
    SELECT batch_id, value AS water
    FROM lab_results
    WHERE analyte = 'water'
  )
  SELECT b.catalyst, COUNT(*) AS n, AVG(w.water) AS mean_water
  FROM batches AS b
  INNER JOIN water AS w ON b.batch_id = w.batch_id
  GROUP BY b.catalyst
")

Catalyst D’s batches come out wettest, at about 242 ppm. But two of its eight water results come from Kestrel’s wet lots. So is it the catalyst, or the raw material? Untangling two causes like that is a job for regression, in Module 2.

Window functions

In Lesson 4 you met window functions in dplyr: ranks, lag() and cumulative sums, which compute a value for every row by looking at its neighbors. SQL has them too, written with OVER:

dbGetQuery(con, "
  SELECT batch_id, reactor, yield_pct,
    RANK() OVER (PARTITION BY reactor ORDER BY yield_pct DESC) AS rank_in_reactor
  FROM batches
  ORDER BY reactor, rank_in_reactor
  LIMIT 5
")
#>   batch_id reactor yield_pct rank_in_reactor
#> 1      B11      R1      74.8               1
#> 2      B07      R1      74.1               2
#> 3      B29      R1      74.0               3
#> 4      B01      R1      70.2               4
#> 5      B33      R1      69.5               5

OVER (...) describes the window. PARTITION BY splits the rows into groups, like group_by(), and ORDER BY sets the order inside each group. Unlike GROUP BY, a window function keeps every row.

SQL dplyr Gives
ROW_NUMBER() row_number() 1, 2, 3, … with no ties
RANK() min_rank() ranks, where ties share a rank, then a gap
DENSE_RANK() dense_rank() ranks, where ties share a rank, with no gap
LAG(x), LEAD(x) lag(x), lead(x) the previous or the next value
SUM(x) OVER (... ORDER BY ...) cumsum(x) a running total
AVG(x) OVER (PARTITION BY g) mean(x) in a grouped mutate() the group’s mean, on every row

Here’s a running total of the alarms on R1, around batch B31, whose alarm count is missing:

dbGetQuery(con, "
  WITH running AS (
    SELECT batch_id, reactor, alarms,
      SUM(alarms) OVER (PARTITION BY reactor ORDER BY start_time) AS running_alarms
    FROM batches
  )
  SELECT * FROM running
  WHERE reactor = 'R1' AND batch_id BETWEEN 'B27' AND 'B35'
")
#>   batch_id reactor alarms running_alarms
#> 1      B27      R1      3             19
#> 2      B29      R1      1             20
#> 3      B31      R1     NA             20
#> 4      B33      R1      1             21
#> 5      B35      R1      2             23

Two things to notice. First, at B31 the running total just carries on, because SQL’s SUM() skips the NULL. In Lesson 4, R’s cumsum() turned everything after B31 into NA. Second, the window is computed inside a CTE, and only filtered afterwards. Window functions run in the SELECT step, after WHERE, so filtering first would cut the windows short. For the same reason, you can’t use a window function inside WHERE at all.

Your turn. Find the best batch on each reactor. Number the batches within each reactor from the highest yield down, then keep number 1.

Partition by reactor, and order by yield_pct DESC, so that number 1 is the highest yield.

dbGetQuery(con, "
  WITH ranked AS (
    SELECT batch_id, reactor, yield_pct,
      ROW_NUMBER() OVER (PARTITION BY reactor ORDER BY yield_pct DESC) AS rn
    FROM batches
  )
  SELECT batch_id, reactor, yield_pct
  FROM ranked
  WHERE rn = 1
")

B11 on R1, at 74.8%, and B16 on R2, at 68.7%. That’s slice_max(yield_pct, n = 1) after group_by(reactor), in SQL.

Creating tables and indexes

So far you’ve only read from the database, but SQL can also build one. To experiment safely, connect to ":memory:": a fresh, empty database that lives only in memory, and disappears when you disconnect.

mem <- dbConnect(RSQLite::SQLite(), ":memory:")
dbExecute(mem, "
  CREATE TABLE analysts (
    analyst_id TEXT PRIMARY KEY,
    name       TEXT NOT NULL
  )
")
#> [1] 0
dbExecute(mem, "INSERT INTO analysts VALUES ('A1', 'Noor'), ('A2', 'Felix')")
#> [1] 2
dbGetQuery(mem, "SELECT * FROM analysts")
#>   analyst_id  name
#> 1         A1  Noor
#> 2         A2 Felix

dbExecute() is for SQL that changes something rather than asking a question, and it returns the number of rows it changed. CREATE TABLE lists each column with its type, plus constraints that the database enforces for you: PRIMARY KEY means that the values must be unique, and NOT NULL forbids missing values. Try breaking the rules:

dbExecute(mem, "INSERT INTO analysts VALUES ('A1', 'Someone else')")
#> Error:
#> ! UNIQUE constraint failed: analysts.analyst_id

That’s the primary key from Lesson 6, now guarded by the database itself. To copy a whole data frame into a database, use dbWriteTable():

dbWriteTable(mem, "lab_results", dbReadTable(con, "lab_results"))
dbListTables(mem)
#> [1] "analysts"    "lab_results"

dbAppendTable() adds rows to a table that already exists, and dbRemoveTable() deletes one. Be aware that dbWriteTable() doesn’t create any keys or constraints. For those, write the CREATE TABLE yourself first, and then append the data.

An index is like the index at the back of a book: a sorted list that lets the database jump straight to the rows it needs, instead of reading the whole table. EXPLAIN QUERY PLAN shows how a query will run:

plan <- "EXPLAIN QUERY PLAN SELECT * FROM lab_results WHERE batch_id = 'B18'"
dbGetQuery(con, plan)$detail
#> [1] "SCAN lab_results"
dbExecute(con, "CREATE INDEX idx_lab_batch ON lab_results (batch_id)")
#> [1] 0
dbGetQuery(con, plan)$detail
#> [1] "SEARCH lab_results USING INDEX idx_lab_batch (batch_id=?)"

Before the index, SQLite has to SCAN all of lab_results. Afterwards, it can SEARCH the index. With 124 rows you’d never notice the difference, but with 124 million it’s the difference between milliseconds and minutes. Index the columns you join and filter on the most, usually the keys. The price is a little extra storage, and slightly slower inserts.

Your turn. The lab results mention three analysts, but in a fresh database the analysts table is empty. Fill it with all three: A1 is Noor, A2 is Felix and A3 is Ada.

Each row goes in brackets, with the text in single quotes, and the rows are separated by commas: ('A1', 'Noor'), ....

mem <- dbConnect(RSQLite::SQLite(), ":memory:")
dbExecute(mem, "CREATE TABLE analysts (analyst_id TEXT PRIMARY KEY, name TEXT NOT NULL)")
dbExecute(mem, "INSERT INTO analysts VALUES ('A1', 'Noor'), ('A2', 'Felix'), ('A3', 'Ada')")
dbGetQuery(mem, "SELECT * FROM analysts")

dbplyr: dplyr that writes SQL

Here’s the twist: you don’t always have to write SQL yourself. The dbplyr package lets you write ordinary dplyr code against a database table. tbl() points at a table without loading it into R:

library(dplyr)
batches_db <- tbl(con, "batches")
by_catalyst <- batches_db |>
  group_by(catalyst) |>
  summarise(n = n(), mean_yield = mean(yield_pct, na.rm = TRUE))
show_query(by_catalyst)
#> <SQL>
#> SELECT `catalyst`, COUNT(*) AS `n`, AVG(`yield_pct`) AS `mean_yield`
#> FROM `batches`
#> GROUP BY `catalyst`

show_query() reveals the SQL that dbplyr wrote for you. Nothing has actually run yet: by_catalyst is a lazy query, a recipe waiting to be cooked. collect() runs it in the database, and brings the result into R as a tibble:

collect(by_catalyst)
#> # A tibble: 4 × 3
#>   catalyst     n mean_yield
#>   <chr>    <int>      <dbl>
#> 1 A           10       60.0
#> 2 B           12       55.7
#> 3 C            9       54.8
#> 4 D            9       60.5

Lazy queries are dbplyr’s superpower. The database does the heavy lifting, and only the small result travels to R, which matters when a table is too big for your computer’s memory. Writing na.rm = TRUE tells dbplyr that you know SQL always skips missing values. Leave it out, and dbplyr reminds you with a warning.

Not every R function has a SQL translation. dbplyr knows the common ones, like arithmetic, comparisons, mean(), n(), if_else() and case_when(). A function it doesn’t know is passed to the database as it is, and the database complains if it doesn’t know it either. When that happens, collect() first, and carry on in R.

Your turn. With dbplyr, compare the two gas chromatographs: count the first-test purity results from each instrument, and compute their mean. Then bring the answer into R.

Keep the purity first tests with filter(analyte == "purity", retest == 0). It’s ordinary dplyr!

The last step runs the query and brings the result into R: collect().

  group_by(instrument_id) |>
  summarise(n = n(), mean_purity = mean(value, na.rm = TRUE)) |>

Challenge round

Challenge 1 · The wet supplier, in SQL. In Lesson 5, you traced batch B18’s wet product back to its supplier with a chain of dplyr joins. Do it again in SQL: find the mean water content for each supplier, from the wettest down.

Three joins, one after another: lab_results to batches by batch_id, batches to lots by lot_id, and lots to suppliers by supplier_id. The query already uses the aliases l and s.

INNER JOIN batches AS b ON l.batch_id = b.batch_id
INNER JOIN lots AS lo ON b.lot_id = lo.lot_id
INNER JOIN suppliers AS s ON lo.supplier_id = s.supplier_id
dbGetQuery(con, "
  SELECT s.name, COUNT(*) AS n, AVG(l.value) AS mean_water
  FROM lab_results AS l
  INNER JOIN batches AS b ON l.batch_id = b.batch_id
  INNER JOIN lots AS lo ON b.lot_id = lo.lot_id
  INNER JOIN suppliers AS s ON lo.supplier_id = s.supplier_id
  WHERE l.analyte = 'water'
  GROUP BY s.name
  ORDER BY mean_water DESC
")

Kestrel Industrial comes out on top again, at about 319 ppm. Same answer, different language.

Challenge 2 · Ties at the top. Find the best batch for each catalyst. This time, use RANK() instead of ROW_NUMBER(), and keep every batch ranked 1. You’ll get one more row than you might expect. Why?

The same window as before, but partitioned by catalyst, and with RANK() in place of ROW_NUMBER().

RANK() OVER (PARTITION BY catalyst ORDER BY yield_pct DESC)

dbGetQuery(con, "
  WITH ranked AS (
    SELECT batch_id, catalyst, yield_pct,
      RANK() OVER (PARTITION BY catalyst ORDER BY yield_pct DESC) AS r
    FROM batches
  )
  SELECT batch_id, catalyst, yield_pct
  FROM ranked
  WHERE r = 1
")

Five rows for four catalysts: B20 and B39 tie at the top of catalyst C, both at 65.2%. RANK() gives both of them rank 1, while ROW_NUMBER() would keep just one of them, chosen arbitrarily. It’s the same tie that slice_max() kept in Lesson 4.

Quick quiz

1. In FROM batches AS b, what is b?

Table aliases keep queries short, and tell SQL which table a column comes from when two tables share a column name.

2. Which join keeps the batches that have no water result?

A LEFT JOIN keeps every row of the left table, filling in NULL where nothing matches. Adding WHERE l.result_id IS NULL then finds the missing tests.

3. Why can’t you write WHERE yield_pct > AVG(yield_pct)?

WHERE yield_pct > (SELECT AVG(yield_pct) FROM batches) computes the average in a subquery first.

4. What does a common table expression (WITH name AS (...)) do?

A CTE only exists while its query runs. It’s a way of building a query in readable steps, much like a pipe.

5. Two batches tie for the highest yield in a group. What do RANK() and ROW_NUMBER() give them?

RANK() shares ranks between ties, like dplyr’s min_rank(). ROW_NUMBER() always counts 1, 2, 3, … and breaks ties arbitrarily.

6. In dbplyr, what does collect() do?

Until you collect(), a dbplyr query is lazy: just a recipe. show_query() shows the recipe, and collect() cooks it.

Wrap-up

That’s a seriously powerful toolkit! Here’s what you’ve learned:

  • Joins: INNER JOIN and LEFT JOIN ... ON, with table aliases. A LEFT JOIN plus IS NULL finds what’s missing.
  • Subqueries: a query in brackets, giving a single value, or a list for IN.
  • CTEs: WITH name AS (...) builds a query in readable steps, like a pipe. CASE WHEN is SQL’s case_when().
  • Window functions: ROW_NUMBER(), RANK(), LAG() and running sums, with OVER (PARTITION BY ... ORDER BY ...). They keep every row, and they run after WHERE.
  • Building: CREATE TABLE with PRIMARY KEY and NOT NULL constraints, INSERT INTO, dbWriteTable(), and CREATE INDEX for speed.
  • dbplyr: tbl(), the usual dplyr verbs, show_query() to see the SQL and collect() to run it.

NoteKey words from this lesson
Table alias
A short nickname for a table in a query, given with AS, as in FROM batches AS b.
INNER JOIN and LEFT JOIN
Joins that keep only matched rows, or every row of the left table.
Subquery
A query inside another query, in brackets.
Common table expression (CTE)
A named query defined with WITH, which the rest of the query can use like a table.
Window function
A function that computes a value for every row from a window of related rows, like RANK() OVER (PARTITION BY ...).
Constraint
A rule that a database enforces, like PRIMARY KEY or NOT NULL.
Index
A sorted lookup structure that lets a database find rows without reading the whole table.
Lazy query
A dbplyr query that hasn’t run yet. collect() runs it.
