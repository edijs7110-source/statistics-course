Many columns at once, neighbors in time, running totals and ranks

Apply functions to many columns with across(), compare rows with their neighbors using lag() and lead(), compute running totals and ranks, and do grouped calculations that keep every row.

Module 1 · Lesson 4 of 14 Week 19 of 160 About 5–7 hours

Module 0 gave you dplyr’s five main verbs. Process data asks for more. You’ll want the same summary for twenty columns at once, the change from one sensor reading to the next, a running total of alarms over the campaign, or the best batch for each catalyst. This lesson adds those tools, and they all slot straight into the pipelines you already know.

Today’s tools are the ones that make process data come alive: heating rates, record batches, running totals. A few small functions, and suddenly you can answer real operational questions.

In this lesson you’ll:

  • apply functions to many columns at once with across()
  • compare each row with its neighbors using lag() and lead()
  • compute running totals and running maximums
  • rank rows and pick the top ones in each group
  • do grouped calculations that keep every row

Many columns at once: across()

To compute the mean of four columns, you could write four lines inside summarise(). across() does it in one: give it the columns, then the function.

batches |>
  group_by(reactor) |>
  summarise(across(c(temp_C, pressure_bar, residence_min, yield_pct), mean))
#> # A tibble: 2 × 5
#>   reactor temp_C pressure_bar residence_min yield_pct
#>   <chr>    <dbl>        <dbl>         <dbl>     <dbl>
#> 1 R1         NA          4.90          47.4      60.9
#> 2 R2        179.         5.08          42.2      54.4

The temperature is NA because two batches have no temperature. To pass na.rm = TRUE, write the function as an anonymous function, with the \(x) shorthand from Module 0:

batches |>
  group_by(reactor) |>
  summarise(across(c(temp_C, pressure_bar, residence_min, yield_pct), \(x) mean(x, na.rm = TRUE)))
#> # A tibble: 2 × 5
#>   reactor temp_C pressure_bar residence_min yield_pct
#>   <chr>    <dbl>        <dbl>         <dbl>     <dbl>
#> 1 R1        180.         4.90          47.4      60.9
#> 2 R2        179.         5.08          42.2      54.4

R1 averages 61% yield, against 54% for R2, with longer residence times. That’s a lead worth following up!

You can pick the columns with the select() helpers you already know, like where(is.numeric) or ends_with("_pct"), and apply several functions at once by giving across() a named list. The new columns are named column_function:

batches |>
  summarise(across(c(yield_pct, residence_min), list(mean = mean, sd = sd)))
#>   yield_pct_mean yield_pct_sd residence_min_mean residence_min_sd
#> 1        57.6475     9.749477              44.75         11.23463

across() works inside mutate() too. Here it rounds every numeric column in one go:

batches |>
  mutate(across(where(is.numeric), \(x) round(x))) |>
  select(batch_id, temp_C:yield_pct) |>
  head(3)
#>   batch_id temp_C pressure_bar residence_min alarms yield_pct
#> 1      B01    185            4            47      1        70
#> 2      B02    176            5            38      1        54
#> 3      B03    178            5            32      1        49

Neighbors in time: lag() and lead()

lag(x) shifts a vector down by one position, so each row sees the previous value. lead(x) looks ahead to the next one. Together they let you compare each row with its neighbors:

x <- c(28, 56, 85, 110)
lag(x)
#> [1] NA 28 56 85
x - lag(x)
#> [1] NA 28 29 25
lead(x)
#> [1]  56  85 110  NA

The first value of lag(x) is NA, because nothing comes before it. In the sensor log, that’s exactly what you need for a heating rate: the change in temperature between readings, divided by the 5 minutes between them.

There’s a catch. The tidy sensor log alternates between the reactors, so a plain lag() would compare an R1 reading with an R2 one! Group by reactor first, and lag() works within each group:

sensor |>
  group_by(reactor) |>
  mutate(rate_C_per_min = (temp_C - lag(temp_C)) / 5) |>
  filter(timestamp >= "2026-03-10 07:10:00", timestamp <= "2026-03-10 07:35:00", reactor == "R2")
#> # A tibble: 6 × 5
#> # Groups:   reactor [1]
#>   timestamp           reactor temp_C press_bar rate_C_per_min
#>   <chr>               <chr>    <dbl>     <dbl>          <dbl>
#> 1 2026-03-10 07:10:00 R2        28.5      1             -0.3 
#> 2 2026-03-10 07:15:00 R2        55.9      1.78           5.48
#> 3 2026-03-10 07:20:00 R2        84.9      2.53           5.8 
#> 4 2026-03-10 07:25:00 R2       110.       3.25           5   
#> 5 2026-03-10 07:30:00 R2       139.       4.03           5.88
#> 6 2026-03-10 07:35:00 R2       166.       4.72           5.4

That’s batch B18 heating up on R2: about 5 to 6 °C per minute.

Always ask “neighbors within what?” before using lag(). The data must be sorted in the right order (use arrange() if you’re not sure) and grouped by whatever separates the series, like the reactor.

Your turn. Find the fastest heating rate on each reactor during the day. Drop the 999.9 °C glitch first, or it will win easily!

The previous reading is lag(temp_C).

sensor |>
  filter(temp_C < 500) |>
  group_by(reactor) |>
  mutate(rate = (temp_C - lag(temp_C)) / 5) |>
  summarise(max_rate = max(rate, na.rm = TRUE))

Both reactors heat at up to about 6 °C per minute.

Running totals and records

The cumulative functions build up a value row by row: cumsum() for a running total, cummax() and cummin() for the largest and smallest so far, and cummean() for the running mean.

alarms <- c(1, 0, 3, 1, 2)
cumsum(alarms)
#> [1] 1 1 4 5 7
cummax(alarms)
#> [1] 1 1 3 3 3

Here’s a running count of alarms on each reactor over the campaign. The batches have to be in time order first:

batches |>
  arrange(start_time) |>
  group_by(reactor) |>
  mutate(cum_alarms = cumsum(alarms)) |>
  select(batch_id, reactor, alarms, cum_alarms) |>
  filter(reactor == "R1") |>
  tail(6)
#> # A tibble: 6 × 4
#> # Groups:   reactor [1]
#>   batch_id reactor alarms cum_alarms
#>   <chr>    <chr>    <int>      <int>
#> 1 B29      R1           1         20
#> 2 B31      R1          NA         NA
#> 3 B33      R1           1         NA
#> 4 B35      R1           2         NA
#> 5 B37      R1           0         NA
#> 6 B39      R1           1         NA

From batch B31 onwards the total is NA, because B31’s alarm log was lost, and once a running total meets an NA, it stays NA. If you’re happy to count the missing value as zero, coalesce(alarms, 0) replaces each NA with 0. (Is zero a fair guess? Lesson 12 is all about questions like that.)

Your turn. Compute each reactor’s running alarm total, counting the missing alarm log as 0, and return each reactor’s total at the end of the campaign.

Inside cumsum(), replace the missing values first: coalesce(alarms, 0).

batches |>
  arrange(start_time) |>
  group_by(reactor) |>
  mutate(cum_alarms = cumsum(coalesce(alarms, 0))) |>
  summarise(total = last(cum_alarms))

24 alarms on R1 and 25 on R2. last() takes the last value in each group.

Ranks and the top of each group

Ranking functions give each row its position in the order of a variable. They differ in how they handle ties:

y <- c(65.2, 74.8, 65.2, 58.1)
min_rank(desc(y))     # ties share the best rank, then a gap: 3 1 3 4
#> [1] 2 1 2 4
dense_rank(desc(y))   # ties share, with no gap: 2 1 2 3
#> [1] 2 1 2 3
row_number(desc(y))   # no ties at all: every row gets its own rank
#> [1] 2 1 3 4

desc() ranks from largest to smallest. To keep the top rows in each group, slice_max() is the quickest way. Here are the two best batches on each reactor:

batches |>
  slice_max(yield_pct, n = 2, by = reactor) |>
  select(batch_id, reactor, yield_pct)
#>   batch_id reactor yield_pct
#> 1      B11      R1      74.8
#> 2      B07      R1      74.1
#> 3      B16      R2      68.7
#> 4      B04      R2      65.3

by = reactor groups for just this one step, the same as group_by(reactor) before it.

Your turn. Find the highest-yielding batch for each catalyst with slice_max().

Order by yield_pct, within each catalyst.

batches |>
  slice_max(yield_pct, n = 1, by = catalyst) |>
  select(batch_id, catalyst, yield_pct)

Five rows for four catalysts? Catalyst C has a tie: B20 and B39 both reached 65.2%, and slice_max() keeps ties unless you add with_ties = FALSE.

Grouped calculations that keep every row

group_by() followed by summarise() collapses each group to one row. Followed by mutate() or filter(), it works within groups but keeps every row. That’s how you compare each batch with its own group, as in Module 0’s last challenge. Here, each batch’s yield as a z-score within its catalyst:

batches |>
  group_by(catalyst) |>
  mutate(z_in_catalyst = (yield_pct - mean(yield_pct)) / sd(yield_pct)) |>
  ungroup() |>
  select(batch_id, catalyst, yield_pct, z_in_catalyst) |>
  head(4)
#> # A tibble: 4 × 4
#>   batch_id catalyst yield_pct z_in_catalyst
#>   <chr>    <chr>        <dbl>         <dbl>
#> 1 B01      B             70.2         1.11 
#> 2 B02      D             53.7        -0.948
#> 3 B03      C             49.2        -0.549
#> 4 B04      B             65.3         0.736

And a grouped filter() keeps rows by a condition that uses the group’s own summaries, like “batches more than 10 points below their catalyst’s mean yield”:

batches |>
  group_by(catalyst) |>
  filter(yield_pct < mean(yield_pct) - 10) |>
  select(batch_id, catalyst, yield_pct)
#> # A tibble: 3 × 3
#> # Groups:   catalyst [2]
#>   batch_id catalyst yield_pct
#>   <chr>    <chr>        <dbl>
#> 1 B10      B             31.1
#> 2 B14      B             33.8
#> 3 B40      C             36.8

Your turn. How many batches have a yield above the mean yield of their own catalyst?

Inside a grouped filter(), mean(yield_pct) is the mean of each batch’s own catalyst: yield_pct > mean(yield_pct).

batches |>
  group_by(catalyst) |>
  filter(yield_pct > mean(yield_pct)) |>
  ungroup() |>
  nrow()

Challenge round

Challenge 1 · When did each reactor reach temperature? Find the first time stamp at which each reactor’s temperature rose to 150 °C or more, coming from below 150 °C at the previous reading. Drop the glitch first.

You want rows where the temperature is now at least 150 and the previous reading was below 150. Combine the two with a comma inside filter().

filter(temp_C >= 150, lag(temp_C) < 150)

sensor |>
  filter(temp_C < 500) |>
  group_by(reactor) |>
  filter(temp_C >= 150, lag(temp_C) < 150) |>
  slice_head(n = 1) |>
  select(timestamp, reactor, temp_C)

R2 reached temperature at 07:35, and R1 at 14:05. Without the glitch filter, R1 would seem to “reach temperature” at 03:15 in the morning, in the middle of nowhere!

Challenge 2 · Record batches. Going through the campaign in time order, which batches set a new yield record, beating every batch before them? Return their batch_ids.

A batch sets a record when its yield equals the highest yield so far, which is cummax(yield_pct).

batches |>
  arrange(start_time) |>
  filter(yield_pct == cummax(yield_pct)) |>
  pull(batch_id)

B02, then B01, B07 and B11. B11’s 74.8% stood for the rest of the campaign. pull() takes a single column out as a vector.

Quick quiz

1. What does summarise(across(c(a, b), mean)) compute?

across() applies the function to each listed column separately.

2. What is lag(c(5, 8, 2))?

Each element is replaced by the one before it. lead() would give 8 2 NA.

3. You compute temp - lag(temp) on sensor data from two reactors, stored in one long table. What else must you do?

Without grouping, lag() would compare a reading from one reactor with a reading from the other.

4. What is cumsum(c(2, NA, 1))?

Once a running total meets a missing value, it stays missing. coalesce(x, 0) is one way around that, if 0 is a fair replacement.

5. Two batches tie for the highest yield in a group. What does slice_max(yield_pct, n = 1) return for that group?

slice_max() keeps ties by default. Add with_ties = FALSE to get exactly one row.

6. group_by(catalyst) |> mutate(m = mean(yield_pct)) gives…

A grouped mutate() keeps every row and computes within groups. summarise() would collapse each group to one row.

Wrap-up

Your dplyr toolkit just got a lot bigger. Here’s what you can do now:

  • Work on many columns: across() applies one or more functions to a set of columns, inside summarise() or mutate().
  • Compare neighbors: lag() and lead() look back and ahead. Sort and group first!
  • Build up values: cumsum(), cummax() and friends give running totals and records. coalesce() fills NAs, when that’s justified.
  • Rank: min_rank(), dense_rank() and row_number() handle ties differently, and slice_max() keeps the top rows of each group.
  • Calculate within groups: a grouped mutate() or filter() compares each row with its own group, and .by groups for a single step.

NoteKey words from this lesson
across()
Applies one or more functions to a set of columns, inside summarise() or mutate().
Anonymous function
A function written where it’s used, like \(x) mean(x, na.rm = TRUE).
lag() and lead()
Shift a vector so that each row sees the previous or the next value.
Window function
A function that returns one value per row, computed from the surrounding rows, like lag(), cumsum() or a rank.
Cumulative function
Builds up a value row by row: cumsum(), cummax(), cummin(), cummean().
Rank
A row’s position in the order of a variable. min_rank(), dense_rank() and row_number() treat ties differently.
coalesce()
Replaces missing values with a given value, or with the first non-missing value from other columns.
