Combining datasets

Keys and joins: connecting batches, lab results, lots and suppliers

Identify primary and foreign keys, combine tables with mutating joins, find matches and mismatches with filtering joins, avoid the classic join pitfalls, and bind tables together.

Module 1 · Lesson 5 of 14 Week 20 of 160 About 5–7 hours

Batch B18’s product had 410 ppm of water, twice the usual. Why? The answer isn’t in any single table. The lab results hold the water content, the batch records say which raw-material lot each batch used, the lots table says which supplier delivered each lot, and the suppliers table has their names. To connect them, you need joins. They’re among the most useful tools in all of data analysis, and by the end of this lesson you’ll have solved the mystery of B18.

Joins are like matching socks: you pair up rows from two tables that share the same ID. Once that clicks, combining any number of tables is easy.

In this lesson you’ll:

  • identify the keys that link tables together
  • add columns from one table to another with left_join() and friends
  • find rows that do and don’t have a match, with semi_join() and anti_join()
  • avoid the classic join pitfalls: duplicate keys and mismatched keys
  • stack tables with bind_rows()

Tables and their keys

Here’s how the plant’s tables fit together:

Table One row per… Key Links to
suppliers supplier supplier_id
lots delivered lot of raw material lot_id suppliers through supplier_id
operators operator operator_id
batches batch batch_id lots through lot_id, operators through operator_id
lab_results lab measurement result_id batches through batch_id

A primary key is a column (or set of columns) that identifies each row uniquely, like batch_id in batches. A foreign key is a column that points to another table’s primary key, like lot_id in batches, which points to a row of lots. Joins work by matching keys.

A primary key must be unique, so it’s worth checking:

batches <- read.csv("data/batches.csv")
lab <- read.csv("data/lab_results.csv")
lots <- read.csv("data/lots.csv")
suppliers <- read.csv("data/suppliers.csv")
operators <- read.csv("data/operators.csv")

batches |> count(batch_id) |> filter(n > 1)
#> [1] batch_id n       
#> <0 rows> (or 0-length row.names)

No duplicates, so batch_id really is a key of batches. In lab_results, though, each batch appears several times, once for each measurement, so there batch_id is a foreign key, and the primary key is result_id.

Your turn. Most batches have three lab results: one each for purity, water and color. Which batches appear four times in lab? (All five tables are ready in every exercise.)

count() makes a column called n. Keep the rows where n == 4.

lab |>
  count(batch_id) |>
  filter(n == 4)

Six batches: their purity was tested twice, because the first result was close to the 98.5% spec.

left_join(): add columns from another table

left_join(x, y) keeps every row of x, and adds the columns of y wherever the keys match. Here’s each batch’s lot, with the lot’s supplier and delivery date added on:

batches |>
  select(batch_id, lot_id) |>
  left_join(lots, by = "lot_id") |>
  head(4)
#>   batch_id  lot_id supplier_id   received assay_pct
#> 1      B01 L26-001          S1 2026-02-02     98.55
#> 2      B02 L26-001          S1 2026-02-02     98.55
#> 3      B03 L26-001          S1 2026-02-02     98.55
#> 4      B04 L26-001          S1 2026-02-02     98.55

by = "lot_id" names the key. You can chain joins, and add the supplier’s name too:

batches |>
  select(batch_id, lot_id) |>
  left_join(lots, by = "lot_id") |>
  left_join(suppliers, by = "supplier_id") |>
  select(batch_id, lot_id, name, country) |>
  head(4)
#>   batch_id  lot_id               name country
#> 1      B01 L26-001 Fizzwell Chemicals     USA
#> 2      B02 L26-001 Fizzwell Chemicals     USA
#> 3      B03 L26-001 Fizzwell Chemicals     USA
#> 4      B04 L26-001 Fizzwell Chemicals     USA

Every batch kept its row and gained columns. That’s a mutating join: it changes the table by adding columns.

Your turn. Add the operators’ names to the batches, then count how many batches each operator ran.

Both tables have an operator_id column. That’s the key.

batches |>
  left_join(operators, by = "operator_id") |>
  count(name)

Maya ran the most batches (11), and Sam the fewest (3).

Solving the water mystery

Now for the question we started with. The path goes through four tables: water results → batches (for the lot) → lots (for the supplier) → suppliers (for the name).

Your turn. Complete the chain of joins, then compute the mean water content for each supplier.

batches links to lots by "lot_id", and lots links to suppliers by "supplier_id".

lab |>
  filter(analyte == "water") |>
  select(batch_id, water_ppm = value) |>
  left_join(batches, by = "batch_id") |>
  left_join(lots, by = "lot_id") |>
  left_join(suppliers, by = "supplier_id") |>
  group_by(name) |>
  summarise(n = n(), mean_water = mean(water_ppm))

Batches made from Kestrel Industrial’s lots average about 320 ppm of water, against roughly 180 to 205 ppm for everyone else. B18 used lot L26-006, a Kestrel lot. Mystery solved: the raw material arrived wet. Notice that select() can rename as it goes: water_ppm = value.

Inner, left, right and full joins

Two batches, B12 and B33, have no water result. What happens to them depends on the kind of join:

water <- lab |> filter(analyte == "water") |> select(batch_id, water_ppm = value)
nrow(left_join(batches, water, by = "batch_id"))     # every batch; NA water for B12 and B33
#> [1] 40
nrow(inner_join(batches, water, by = "batch_id"))    # only batches with a match in both
#> [1] 38
nrow(full_join(batches, water, by = "batch_id"))     # everything from both tables
#> [1] 40
Join Keeps
left_join(x, y) every row of x
right_join(x, y) every row of y
inner_join(x, y) only the rows with a match in both
full_join(x, y) every row of both, matched where possible

left_join() is the one you’ll use most, because it never loses rows from your main table. An inner_join() silently drops anything without a match, which is easy to miss.

Your turn. How many rows does an inner join of the batches with the color results give?

The function is inner_join.

color <- lab |> filter(analyte == "color") |> select(batch_id, color_apha = value)
nrow(inner_join(batches, color, by = "batch_id"))

40: every batch had its color measured, so nothing is dropped.

Filtering joins: who has a match?

Sometimes you don’t want columns from the other table, just to know whether a match exists. Filtering joins keep or drop rows of x without adding anything:

  • semi_join(x, y) keeps the rows of x that have a match in y.
  • anti_join(x, y) keeps the rows of x that don’t.

anti_join() is a data detective’s best friend. It finds the batches missing a test, lab results for batches that don’t exist, and lots that were never used:

semi_join(batches, water, by = "batch_id") |> nrow()
#> [1] 38

Your turn. Which batches have no water result?

You want the batches without a match: anti_join.

water <- lab |> filter(analyte == "water")
batches |>
  anti_join(water, by = "batch_id") |>
  select(batch_id)

B12 and B33. Someone should ask the lab what happened to those samples.

Join pitfalls

Joins are powerful, and they go wrong in a few classic ways.

Duplicate keys multiply rows. Join the purity results to the batches, and you get 46 rows, not 40, because the six re-tested batches match two purity results each:

purity <- lab |> filter(analyte == "purity") |> select(batch_id, purity = value, retest)
nrow(left_join(batches, purity, by = "batch_id"))
#> [1] 46

If you expect one match per row, say so with relationship = "one-to-one", and dplyr stops with an error when it isn’t true, instead of quietly adding rows:

left_join(batches, purity, by = "batch_id", relationship = "one-to-one")
#> Error in `left_join()`:
#> ! Each row in `x` must match at most 1 row in `y`.
#> ℹ Row 19 of `x` matches multiple rows in `y`.

Keys with different names. When the key columns are named differently, use join_by(), which reads like a sentence: “match batch in the first table with batch_id in the second”.

notes <- data.frame(batch = c("B07", "B18"), note = c("re-sampled", "high water"))
notes |> left_join(batches, by = join_by(batch == batch_id)) |> select(batch, note, reactor)
#>   batch       note reactor
#> 1   B07 re-sampled      R1
#> 2   B18 high water      R2

Keys that look the same but aren’t. "B07" and "b07" don’t match, and nor do "B07" and "B07 " with a trailing space, or the number 7 and the text "7". A mismatched key doesn’t cause an error. It just quietly gives NAs. Lesson 10 shows how to clean keys like these, and an anti_join() is the quickest way to check for them.

Your turn. Join the purity results to the batches without duplicating any batch: keep only the first tests, and add relationship = "one-to-one" to prove it.

The re-tests have retest equal to TRUE, so keep the rows where it isn’t: !retest.

purity <- lab |> filter(analyte == "purity", !retest) |> select(batch_id, purity = value)
batches |>
  left_join(purity, by = "batch_id", relationship = "one-to-one") |>
  nrow()

Your turn. The shift notes below use the column name batch instead of batch_id. Join them to the batches with join_by(), keeping the note, the reactor and the yield.

Inside join_by(), put the first table’s column on the left: batch == batch_id.

notes <- data.frame(batch = c("B07", "B18", "B33"), note = c("re-sampled", "high water", "no water test"))
notes |>
  left_join(batches, by = join_by(batch == batch_id)) |>
  select(batch, note, reactor, yield_pct)

Stacking tables: bind_rows()

Joins combine tables side by side, by key. Sometimes you just want to stack tables with the same columns on top of each other, like two shifts’ logs or two months of results. That’s bind_rows(), from Lesson 2:

day_log <- data.frame(batch_id = c("B01", "B02"), shift = "day")
night_log <- data.frame(batch_id = c("B04", "B07"), shift = "night")
bind_rows(day_log, night_log)
#>   batch_id shift
#> 1      B01   day
#> 2      B02   day
#> 3      B04 night
#> 4      B07 night

There’s also bind_cols(), which glues tables side by side by row position. Avoid it unless you’re certain the rows line up. One unnoticed sort, and every row is matched with the wrong partner. A join by key is always safer.

Challenge round

Challenge 1 · Does experience matter? Do operators with more years of experience get better yields? Join the operators to the batches, and compute the correlation between years_experience and yield_pct.

left_join(operators, by = "operator_id") brings each batch’s operator’s experience along.

joined <- batches |> left_join(operators, by = "operator_id")
cor(joined$years_experience, joined$yield_pct)

About 0.08: practically no relationship. The plant’s yields depend on residence time and alarms (Module 0), not on who’s running the batch. That’s good news for the newer operators!

Challenge 2 · Find the orphans. Some late color results arrived, keyed by a column called batch. Which of them belong to a batch that doesn’t exist in batches?

You want the rows of late without a match in batches, matching batch with batch_id.

anti_join(batches, by = join_by(batch == batch_id))

late <- data.frame(batch = c("B05", "B5", "B41", "B22"), analyte = "color", value = c(14, 15, 22, 18))
late |>
  anti_join(batches, by = join_by(batch == batch_id))

B5 is probably B05 typed without its zero, and B41 belongs to April’s campaign, which isn’t in this table. Both need checking before they’re loaded, which is exactly what Lesson 11 is about.

Quick quiz

1. What makes a column a primary key?

A primary key has one distinct value per row. Check with count(table, key) |> filter(n > 1).

2. batches has 40 rows, and every batch has one lot. What does left_join(batches, lots, by = "lot_id") return?

A left join keeps every row of the first table and adds columns from the second.

3. Which join keeps only the rows with a match in both tables?

An inner join silently drops rows without a match, so check row counts before and after.

4. You want the batches that have no lab result at all. Which function finds them?

anti_join() keeps the rows of the first table that have no match in the second.

5. After a left join, your table has more rows than before. What’s the most likely reason?

Each duplicate match adds a row. Use relationship = "one-to-one" when you expect exactly one match.

6. A join gives NAs where you expected matches. Which is a likely cause?

Keys must match exactly. Case, spaces and types all matter. An anti_join() shows which ones failed.

Wrap-up

You can now connect any tables you’re given. Here’s what you’ve learned:

  • Keys: a primary key identifies each row of a table; a foreign key points to another table’s primary key.
  • Mutating joins add columns: left_join() keeps every row of the first table, inner_join() only the matches, full_join() everything.
  • Filtering joins keep or drop rows: semi_join() keeps those with a match, anti_join() those without.
  • Pitfalls: duplicate keys multiply rows (use relationship), differently named keys need join_by(), and nearly identical keys don’t match at all.
  • Stacking: bind_rows() stacks tables with the same columns. Prefer joins to bind_cols().

NoteKey words from this lesson
Primary key
A column, or set of columns, whose values identify each row of a table uniquely.
Foreign key
A column whose values point to the primary key of another table.
Mutating join
A join that adds columns from one table to another: left_join(), inner_join(), right_join(), full_join().
Filtering join
A join that keeps or drops rows without adding columns: semi_join() and anti_join().
join_by()
Describes how the keys match, including keys with different names, like join_by(batch == batch_id).
Relationship
How many rows of each table can match: one-to-one, one-to-many or many-to-many.
Orphan
A row whose foreign key matches nothing in the table it should point to.
