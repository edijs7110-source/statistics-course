Asking a database questions: SELECT, WHERE, GROUP BY and friends

Connect to a SQLite database from R with DBI, and write SQL queries that select, filter, sort, count and summarize data by group.

Module 1 · Lesson 7 of 14 Week 22 of 160 About 5–7 hours

Most of the world’s data lives in databases: the plant’s laboratory system, a hospital’s patient records, every online shop’s orders. And the language almost every database speaks is SQL (Structured Query Language, often pronounced “sequel”). It’s over fifty years old, it’s on every data job description, and the good news is that you already know its ideas, because dplyr was designed after it. In this lesson you’ll query the plant’s database directly, in SQL, from R.

SQL reads almost like English: “SELECT these columns FROM this table WHERE this is true.” If you can say what you want, you can write the query!

In this lesson you’ll:

  • connect to a database from R, and look around it
  • choose columns with SELECT, and filter rows with WHERE
  • sort with ORDER BY, and keep the top rows with LIMIT
  • count and summarize with aggregate functions
  • summarize by group with GROUP BY, and filter groups with HAVING

Databases and SQL

A database management system (DBMS) stores tables and answers questions about them. Big organizations use servers like PostgreSQL, Microsoft SQL Server or Oracle. SQLite is different: the whole database is a single file, with no server needed. It’s the most widely used database in the world (every smartphone has dozens of SQLite files on it), and it’s perfect for learning and for small projects.

The plant’s data is in plant.sqlite, with the same six tables as Lessons 5 and 6. In R, the DBI package talks to databases, and RSQLite is its driver for SQLite:

library(DBI)
con <- dbConnect(RSQLite::SQLite(), "data/plant.sqlite")
dbListTables(con)
#> [1] "batches"     "instruments" "lab_results" "lots"        "operators"  
#> [6] "suppliers"
dbListFields(con, "batches")
#>  [1] "batch_id"      "reactor"       "start_time"    "end_time"     
#>  [5] "operator_id"   "lot_id"        "catalyst"      "temp_C"       
#>  [9] "pressure_bar"  "residence_min" "alarms"        "yield_pct"

con is a connection: think of it as a phone line to the database. dbGetQuery() sends a query down the line and brings the answer back as a data frame:

dbGetQuery(con, "SELECT batch_id, reactor, yield_pct FROM batches LIMIT 5")
#>   batch_id reactor yield_pct
#> 1      B01      R1      70.2
#> 2      B02      R2      53.7
#> 3      B03      R1      49.2
#> 4      B04      R2      65.3
#> 5      B05      R1      53.4

The query is just a piece of text. By convention, SQL keywords are written in capitals, but SQL doesn’t actually care. When you’re finished, hang up with dbDisconnect(con).

SELECT * means “every column”. It’s handy for a quick look, but in real queries it’s better to name the columns you need.

SELECT: choosing columns

SELECT lists the columns you want, separated by commas, and FROM names the table. You can also compute new columns, and name them with AS:

dbGetQuery(con, "SELECT batch_id, yield_pct / 100 AS yield_fraction FROM batches LIMIT 3")
#>   batch_id yield_fraction
#> 1      B01          0.702
#> 2      B02          0.537
#> 3      B03          0.492

That’s select() and mutate() from dplyr, rolled into one.

Your turn. Get the batch_id, catalyst and yield_pct of every batch. (con is ready in every exercise.)

List the three columns after SELECT, separated by commas: batch_id, catalyst, yield_pct.

dbGetQuery(con, "SELECT batch_id, catalyst, yield_pct FROM batches")

WHERE: filtering rows

WHERE keeps the rows where a condition is true, just like filter(). A few things look a little different from R:

In SQL In R Meaning
= == equals
<> or != != doesn’t equal
AND, OR, NOT &, |, ! combine conditions
'R1' "R1" text, in single quotes
IN ('A', 'D') %in% c("A", "D") is one of
BETWEEN 170 AND 180 >= 170 & <= 180 in a range, ends included
LIKE 'B1%' startsWith(x, "B1") matches a pattern: % means “anything”
IS NULL is.na() missing (SQL calls it NULL) 
dbGetQuery(con, "SELECT batch_id, residence_min, yield_pct FROM batches WHERE residence_min > 60")
#>   batch_id residence_min yield_pct
#> 1      B04          60.7      65.3
#> 2      B07          64.0      74.1
#> 3      B29          71.7      74.0
#> 4      B33          65.4      69.5
dbGetQuery(con, "SELECT batch_id, temp_C FROM batches WHERE temp_C IS NULL")
#>   batch_id temp_C
#> 1      B07     NA
#> 2      B23     NA
Warning= NULL never matches

In SQL, a comparison with a missing value is never true, so WHERE temp_C = NULL returns nothing at all, just like x == NA in R. Always write IS NULL or IS NOT NULL.

Because the whole query is inside R’s double quotes, text values in SQL use single quotes. That’s a happy accident: the two kinds of quotes don’t clash.

Your turn. Find the batches that ran on reactor 'R2' and had a yield above 60%.

Two conditions joined with AND: reactor = 'R2' AND yield_pct > 60. Note the single quotes around R2.

dbGetQuery(con, "SELECT batch_id, yield_pct FROM batches WHERE reactor = 'R2' AND yield_pct > 60")

Only five of R2’s 20 batches beat 60%.

Your turn. Which batch has a missing alarm count?

Missing values in SQL are NULL, and you test for them with IS NULL.

dbGetQuery(con, "SELECT batch_id, alarms FROM batches WHERE alarms IS NULL")

ORDER BY and LIMIT

ORDER BY sorts the result, smallest first; add DESC for largest first. LIMIT keeps only the first few rows. Together they find the top or bottom of anything:

dbGetQuery(con, "SELECT batch_id, yield_pct FROM batches ORDER BY yield_pct DESC LIMIT 3")
#>   batch_id yield_pct
#> 1      B11      74.8
#> 2      B07      74.1
#> 3      B29      74.0

Your turn. From lab_results, find the three lowest purity results, with their batch_id and value.

Sort by value, smallest first (the default), and keep three rows: ORDER BY value LIMIT 3.

dbGetQuery(con, "SELECT batch_id, value FROM lab_results WHERE analyte = 'purity' ORDER BY value LIMIT 3")

B10, B08 and B13, three batches that all ran hotter than 185 °C.

Aggregate functions

SQL’s aggregate functions summarize many rows into one, like summarise():

Function Gives
COUNT(*) the number of rows
COUNT(column) the number of non-missing values in a column
SUM(), AVG() the total and the mean
MIN(), MAX() the smallest and largest 
dbGetQuery(con, "SELECT COUNT(*) AS n, MIN(yield_pct) AS worst, MAX(yield_pct) AS best FROM batches")
#>    n worst best
#> 1 40  31.1 74.8

Unlike R’s mean(), SQL’s aggregates quietly skip missing values, with no na.rm needed. That’s convenient, but it’s also why you should know how many values were missing.

Your turn. In one query, count all the batches (n), count the batches that have a temperature (n_temp), and compute the mean yield (mean_yield).

COUNT(temp_C) counts only the non-missing temperatures, and AVG(yield_pct) is the mean yield.

dbGetQuery(con, "SELECT COUNT(*) AS n, COUNT(temp_C) AS n_temp, AVG(yield_pct) AS mean_yield FROM batches")

40 batches, 38 of them with a temperature, and a mean yield of 57.6%.

GROUP BY and HAVING

GROUP BY splits the rows into groups, so the aggregates are computed once per group. It’s group_by() plus summarise():

dbGetQuery(con, "
  SELECT catalyst, COUNT(*) AS n, ROUND(AVG(yield_pct), 1) AS mean_yield
  FROM batches
  GROUP BY catalyst
")
#>   catalyst  n mean_yield
#> 1        A 10       60.0
#> 2        B 12       55.7
#> 3        C  9       54.8
#> 4        D  9       60.5

A query can span several lines, which makes longer ones much easier to read.

To filter groups by their summaries, use HAVING. WHERE filters rows before they’re grouped, and HAVING filters groups after:

dbGetQuery(con, "
  SELECT catalyst, COUNT(*) AS n, ROUND(AVG(yield_pct), 1) AS mean_yield
  FROM batches
  GROUP BY catalyst
  HAVING AVG(yield_pct) > 57
")
#>   catalyst  n mean_yield
#> 1        A 10       60.0
#> 2        D  9       60.5

Your turn. For each reactor, count the batches (n) and compute their mean yield (mean_yield).

Add GROUP BY reactor at the end.

dbGetQuery(con, "
  SELECT reactor, COUNT(*) AS n, AVG(yield_pct) AS mean_yield
  FROM batches
  GROUP BY reactor
")

R1 averages about 61% and R2 about 54%, the same gap you found with dplyr in Lesson 4.

SQL and dplyr side by side

You’ve now met the core of SQL, and every piece has a dplyr twin:

SQL dplyr
SELECT a, b select(a, b)
SELECT a / 100 AS c mutate(c = a / 100)
FROM table the data you pipe in
WHERE condition filter(condition)
GROUP BY g group_by(g)
COUNT(*), AVG(x) n(), mean(x, na.rm = TRUE)
HAVING condition filter() after summarise()
ORDER BY x DESC arrange(desc(x))
LIMIT 5 head(5) or slice_head(n = 5)

One difference catches everyone out. You write the clauses in the order SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, but the database runs them in this order:

  1. FROM: find the table.
  2. WHERE: filter the rows.
  3. GROUP BY: form the groups.
  4. HAVING: filter the groups.
  5. SELECT: compute the output columns.
  6. ORDER BY, then LIMIT.

That explains a classic puzzle: you can’t use a name from SELECT ... AS inside WHERE, because WHERE runs before the name exists. (SQLite is lenient here, but most databases aren’t.)

Challenge round

Challenge 1 · Busy operators. Which operators ran more than 8 batches? Return their operator_id and the number of batches, n.

Group by operator first, then filter the groups by their count.

GROUP BY operator_id HAVING COUNT(*) > 8

dbGetQuery(con, "
  SELECT operator_id, COUNT(*) AS n
  FROM batches
  GROUP BY operator_id
  HAVING COUNT(*) > 8
")

OP1 (Maya, 11 batches) and OP5 (Lena, 9). Next lesson, you’ll join in their names with SQL.

Challenge 2 · A lab summary. For each analyte, count the results and compute their mean value, leaving out the re-tests, and sort by analyte. In the database, retest is stored as 0 for a first test and 1 for a re-test, because SQLite has no TRUE and FALSE.

Three clauses, in this order: WHERE to drop the re-tests, GROUP BY the analyte, ORDER BY the analyte.

WHERE retest = 0 GROUP BY analyte ORDER BY analyte

dbGetQuery(con, "
  SELECT analyte, COUNT(*) AS n, AVG(value) AS mean_value
  FROM lab_results
  WHERE retest = 0
  GROUP BY analyte
  ORDER BY analyte
")

40 color results, 40 purity and 38 water. The water count is 38, not 40, because two tests were never run.

Quick quiz

1. What does SELECT * FROM lots return?

* means all the columns, and with no WHERE you get all the rows.

2. How do you write the text value R1 in a SQL condition?

Text values in SQL use single quotes, which conveniently don’t clash with the double quotes around the query in R.

3. WHERE temp_C = NULL returns no rows, even though two temperatures are missing. Why?

Just like x == NA in R, comparing with an unknown gives an unknown. IS NULL asks the right question.

4. What’s the difference between COUNT(*) and COUNT(temp_C)?

40 rows, but only 38 temperatures.

5. What’s the difference between WHERE and HAVING?

Use WHERE for conditions on single rows, and HAVING for conditions on group summaries, like COUNT(*) > 8.

6. Which dplyr verb matches SQL’s ORDER BY yield_pct DESC?

ORDER BY sorts, like arrange(), and DESC is desc().

Wrap-up

You can talk to databases now! Here’s what you’ve learned:

  • Connect: dbConnect() opens a connection, dbGetQuery() sends SQL and returns a data frame, and dbDisconnect() closes it.
  • Choose and filter: SELECT picks and computes columns, FROM names the table, and WHERE filters rows, with IN, BETWEEN, LIKE and IS NULL.
  • Sort: ORDER BY ... DESC and LIMIT find the top and bottom of anything.
  • Summarize: COUNT, SUM, AVG, MIN and MAX skip missing values; GROUP BY makes one row per group; HAVING filters the groups.
  • Order of execution: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
