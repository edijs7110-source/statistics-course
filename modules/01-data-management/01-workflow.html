Projects, folders, file names and version control: habits that save you hours

Organize an analysis as an RStudio project, build file paths that work anywhere, name files and variables well, keep raw data read-only, and track your work with Git.

Welcome to Module 1! In Module 0, every analysis was a single file. Real projects aren’t like that. A study of the pilot plant might involve the lab’s spreadsheets, the batch records, a sensor log, a cleaned dataset, a dozen scripts, twenty figures and a report. Six months later, your supervisor asks: “How exactly did you get that number?” This lesson is about the habits that let you answer in thirty seconds: projects, a sensible folder structure, good file names, reports that rebuild themselves, and version control.

These habits feel like extra work for about a week. After that, they save you hours every month. Future you will be so grateful!

In this lesson you’ll:

  • organize work as a project with a standard folder structure
  • build file paths that work on any computer
  • name files and variables so they sort and search well
  • read and write files from R, and keep raw data safe
  • see what version control is, and how Git fits in

Why reproducibility matters

An analysis is reproducible when someone else (or you, later) can start from the raw data and get exactly the same results by rerunning your code. That sounds obvious, but it fails all the time. Somebody fixes a typo by hand in a spreadsheet, filters some rows with the mouse, copies a number into a report, and a week later nobody can say which version of the data the report came from.

The cure is a simple rule: every step from raw data to final result is done by code. Raw files are never edited. Cleaning, combining, analyzing and plotting all happen in scripts. If the lab sends a corrected file, you drop it in and rerun everything.

That’s how the rest of this module works too. You’ll meet the pilot plant’s whole data system: the batch records, the lab results, the raw-material lots and their suppliers, the operators, the instruments and a sensor log. All of it is for the same 40 batches you analyzed in Module 0.

Projects and folders

An RStudio project is just a folder with a small .Rproj file in it. When you open the project, RStudio sets the working directory to that folder, so every file path can start from there. One project per analysis, always.

Inside it, a standard structure means you (and everyone you work with) always know where things are:

plant-study/
├── plant-study.Rproj
├── README.md      ← what this project is, and how to run it
├── data-raw/      ← files exactly as you received them. Never edit these!
├── data/          ← cleaned data, written by your scripts
├── R/             ← scripts and functions
├── output/        ← figures and tables, written by your scripts
└── reports/       ← Quarto reports

The split between data-raw/ and data/ is the important part. Raw data is read-only; anything in data/ can be deleted and rebuilt by rerunning the scripts.

folders <- c("data-raw", "data", "R", "output")

  dir.create(f, showWarnings = FALSE)

showWarnings = FALSE keeps dir.create() quiet when a folder already exists, like data here.

File paths that work anywhere

A path tells R where a file is. An absolute path starts from the top of the computer, like C:/Users/maya/Desktop/plant-study/data-raw/lab.csv. It works on Maya’s laptop and nowhere else. A relative path starts from the working directory, like data-raw/lab.csv, and works for anyone who opens the project.

So two rules:

  • Use relative paths, from the project folder.
  • Never put setwd() in a script. If a script starts with setwd("C:/Users/maya/..."), it breaks on every other computer.

file.path() glues the pieces of a path together with /, which works on Windows, Mac and Linux alike:

file.path("data-raw", "lab", "results.csv")
#> [1] "data-raw/lab/results.csv"
basename("data-raw/lab/results.csv")    # just the file name
#> [1] "results.csv"
dirname("data-raw/lab/results.csv")     # just the folder
#> [1] "data-raw/lab"
tools::file_ext("data-raw/lab/results.csv")
#> [1] "csv"
WarningBackslashes are a trap

Windows shows paths with backslashes, like C:\new\test.csv, but in R a backslash starts a special character: "\n" is a new line and "\t" is a tab! Use forward slashes ("C:/new/test.csv"), which R understands on Windows too, or better, file.path().

list.files() lists the files in a folder, and its pattern argument picks out names matching a pattern. Here, names ending in .csv:

Naming things

Good file names are a gift to your future self. They follow three principles:

  1. Machine-readable. No spaces, no accents, no special characters. Use letters, numbers, - and _.
  2. Human-readable. Say what’s in the file: lab_results_raw.csv, not data2_final_FINAL.csv.
  3. Sorted sensibly. Put dates first in the form YYYY-MM-DD (the ISO 8601 standard), and pad numbers with zeros.

Watch what happens when numbers aren’t padded:

sort(c("batch_B1.csv", "batch_B2.csv", "batch_B10.csv"))
#> [1] "batch_B1.csv"  "batch_B10.csv" "batch_B2.csv"
sort(c("batch_B01.csv", "batch_B02.csv", "batch_B10.csv"))
#> [1] "batch_B01.csv" "batch_B02.csv" "batch_B10.csv"

Text sorts character by character, so B10 comes before B2. That’s why the plant numbers its batches B01 to B40. Dates have the same problem: 05-03-2026 and 03-05-2026 sort wrongly and mean different days in Europe and the US, while 2026-03-05 is unambiguous and sorts correctly.

sprintf() builds names like these. In its template, %02d means “a whole number, padded with zeros to 2 digits”, and %s means “a piece of text”:

sprintf("batch_B%02d_%s.csv", c(7, 18), "2026-03-10")
#> [1] "batch_B07_2026-03-10.csv" "batch_B18_2026-03-10.csv"

The same thinking applies to variable names: lower case, words joined by underscores, and units in the name, like temp_C and residence_min. Lesson 11 shows a function that cleans up messy names automatically.

Raw data in, clean data out

Here’s the whole idea in miniature. A script reads a raw file, does its work, and writes the result to a new file. It never overwrites the raw data:

lab <- read.csv("data/lab_results.csv")
purity <- lab[lab$analyte == "purity" & !lab$retest, ]
dir.create("output", showWarnings = FALSE)
write.csv(purity, "output/purity_first_tests.csv", row.names = FALSE)
nrow(read.csv("output/purity_first_tests.csv"))
#> [1] 40

row.names = FALSE stops write.csv() adding a column of row numbers, which you almost never want. Because the output is made by code, it can always be deleted and rebuilt. That’s the whole point.

A handy habit: number your scripts in the order they run, like R/01_import.R, R/02_clean.R, R/03_analysis.R. Then anyone can rebuild your project by running them from top to bottom.

Your turn. Read data/lab_results.csv, keep only the water results, write them to output/water.csv (without row names), then read the new file back and return its number of rows.

The analyte is called "water", and the file to write is "output/water.csv".

dir.create("output", showWarnings = FALSE)
lab <- read.csv("data/lab_results.csv")
water <- lab[lab$analyte == "water", ]
write.csv(water, "output/water.csv", row.names = FALSE)
nrow(read.csv("output/water.csv"))

Reports that rebuild themselves

You wrote a Quarto report in the Module 0 project. That’s the last piece of a reproducible workflow: the report contains the code, so every table, figure and number is recomputed whenever you render it. Quarto can even put a number from R right into a sentence: writing `r round(mean(yield), 1)` in your text prints the current mean yield there, and it updates whenever the data changes.

So never copy numbers from R into a report by hand. Copied numbers go stale, and stale numbers are how embarrassing mistakes end up in final reports.

Version control with Git

Have you ever had files called report_v2.docx, report_v3_final.docx and report_v3_final_REALLY.docx? Version control solves that properly. Git, the most popular version-control system, keeps the complete history of a project folder:

  • A repository is a project folder whose history Git tracks.
  • A commit is a snapshot of the files at one moment, with a short message saying what changed, like “Remove duplicate lab results”.
  • The history is the list of commits. You can see exactly what changed between any two, and go back to any of them.
  • A remote, such as a repository on GitHub, is a copy on a server. You push your commits to it and pull other people’s.

RStudio has a Git pane built in, with buttons for committing, pushing and pulling, so you hardly ever need the command line. Commit whenever you finish a small piece of work, with a message that would make sense to a stranger.

ImportantSome things should never go into a repository

Passwords, API keys and confidential data don’t belong in Git, especially on a public site like GitHub: once pushed, they’re very hard to remove from the history. List files Git should ignore in a file called .gitignore. Very large data files are usually kept out too.

Challenge round

Challenge 1 · Read a whole folder. Read every CSV file in the data folder, and return a named vector with the number of rows in each file.

lapply() applies a function to every element: here, read.csv to every file path. Then sapply(tables, nrow) counts the rows of each table.

files <- list.files("data", pattern = "\\.csv$", full.names = TRUE)
tables <- lapply(files, read.csv)
names(tables) <- basename(files)
sapply(tables, nrow)

full.names = TRUE keeps the folder in each path, so read.csv() can find the files.

Challenge 2 · Tidy up column names. A spreadsheet has the column names below. Turn them into clean variable names: lower case, % written as pct, and every run of other characters replaced by a single underscore, with no underscore at the start or end. You should get batch_id, temp_c, pressure_bar and yield_pct.

You want a pattern meaning “one or more characters that aren’t a lower-case letter or a digit”. In a regular expression, that’s "[^a-z0-9]+".

messy <- c("Batch ID", "Temp (C)", "Pressure (bar)", "Yield %")
x <- tolower(messy)
x <- gsub("%", "pct", x, fixed = TRUE)
x <- gsub("[^a-z0-9]+", "_", x)
x <- gsub("^_|_$", "", x)
x

The last line removes underscores at the start (^_) or end (_$), which is where (C) would otherwise leave one.

Quick quiz

1. The lab sends you a spreadsheet with an obvious typo. What should you do?

Raw data stays read-only. A fix in code is documented and repeatable, and it can be undone.

2. Which path will work when a colleague opens your project on their computer?

A relative path starts from the project folder, wherever that is. An absolute path only exists on one computer.

3. Which file name sorts correctly by date and means the same thing everywhere?

ISO 8601 dates (year, month, day) sort correctly as text, and nobody mixes up the day and the month.

4. What does a Git commit record?

A commit is a saved snapshot in the project’s history. It only reaches GitHub when you push it.

5. What should never go into a public GitHub repository?

Anything pushed to a public repository can be seen, and copied, by anyone. List sensitive files in .gitignore.

6. Why build reports with Quarto instead of pasting numbers into a word processor?

Reports built by code stay in sync with the data. Pasted numbers quietly go out of date.

Wrap-up

Your projects are about to get a lot tidier. Here’s what you can do now:

  • Work reproducibly: every step from raw data to result is done by code, and raw files are never edited.
  • Organize: one RStudio project per analysis, with folders like data-raw/, data/, R/ and output/.
  • Point to files well: relative paths, built with file.path(), and no setwd() in scripts.
  • Name things well: machine-readable, human-readable, ISO dates and zero-padded numbers.
  • Track your work: Git keeps a history of commits, and GitHub keeps a copy on a server. Secrets stay out.
