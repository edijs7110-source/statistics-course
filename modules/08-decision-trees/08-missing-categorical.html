Missing values and categorical inputs

Surrogates, missingness codes and 60 sales reps

Real business data have gaps and messy categories. See how rpart routes accounts with a missing satisfaction score through surrogate splits, compare surrogates with imputation and with coding the gap as information, and check that trees don’t care about monotone transformations. Then tackle an input with 60 levels: see how noisy each sales rep’s churn rate is, shrink it toward the average, encode it without leaking, and find out what each approach does to the validation AUC.

Module 8 · Lesson 8 of 13 Week 126 of 160 About 5–7 hours

Two things in the churn data have been set aside since Lesson 1: the satisfaction score, missing for almost a third of the accounts, and the sales rep, an input with 60 levels. Both are typical of business data, and both need care, for opposite reasons. Missing values are a gap in the information; a 60-level category is too much freedom for a tree to search. This lesson deals with each.

Missing values aren’t always a nuisance. Sometimes the fact that a customer didn’t answer the survey is the most honest answer of all!

In this lesson you’ll:

  • check whether missingness carries information
  • see how rpart’s surrogate splits route cases with missing values
  • compare surrogates, imputation and missingness codes on the validation set
  • see that monotone transformations don’t change a tree
  • measure how noisy a 60-level category’s per-level rates are
  • shrink them with smoothed target encoding, out of fold, and see the leakage when you don’t

Is missing informative?

The setup code makes Lesson 1’s partition, and defines auc().

Your turn. Compare the churn rate and the average number of complaints of the training accounts with and without a satisfaction score.

The input with gaps is satisfaction.

miss <- is.na(train$satisfaction)
rbind(n = table(miss), churn_rate = tapply(train$churned == "yes", miss, mean),
      complaints = tapply(train$complaints, miss, mean))

599 of the 1,962 training accounts have no score. They churned at 22.7%, against 18.5% for those who answered, and they complained more (0.85 complaints a year, against 0.65). Unhappy customers are less likely to fill in a survey. In Module 1’s terms, the data are missing not at random: the missingness depends on the very thing the score would have measured. So the gap is itself information, and a model should be able to use it.

Surrogate splits

When rpart splits a node on an input, it also looks for surrogate splits: splits on other inputs that send the cases to the same side as the primary split as often as possible. When a case’s primary input is missing, rpart uses the best available surrogate; if none is available, it sends the case in the majority direction.

Your turn. Grow a one-split tree on four inputs, chosen so that the root splits on the satisfaction score, and look at its splits table: the primary split and its surrogates.

One split: maxdepth = 1.

stump <- rpart(churned ~ satisfaction + complaints + visits + payment_days, data = train, method = "class",
               control = rpart.control(maxdepth = 1, cp = 0))
print(stump)
stump$splits

The root splits on a satisfaction score below 4.5: 76 accounts, 54% of them churners, against 18% for the rest. The splits table lists the primary split and the runners-up (count is the number of cases with the input observed), and below them the surrogate: complaints of 4.5 or more, with an adj of 0.027. adj measures how much better the surrogate predicts the primary split’s direction than simply following the majority: 0 means no better, 1 means perfectly. Here the surrogate is barely better than the majority rule, so for the 599 accounts without a score, rpart is close to guessing.

Your turn. Predict the validation accounts without a score, with surrogates (the default) and with surrogates switched off (usesurrogate = 0).

usesurrogate = 0 switches them off.

f <- churned ~ satisfaction + complaints + visits + payment_days
with_s <- rpart(f, data = train, method = "class", control = rpart.control(maxdepth = 1, cp = 0))
without_s <- rpart(f, data = train, method = "class", control = rpart.control(maxdepth = 1, cp = 0, usesurrogate = 0))
na <- is.na(valid$satisfaction)
list(with_surrogates = table(round(predict(with_s, valid[na, ])[, "yes"], 3)),
     without = table(round(predict(without_s, valid[na, ])[, "yes"], 3)))

With surrogates, all 330 validation accounts without a score get 0.184: none of them has 5 or more complaints, so the surrogate sends every one to the large, low-risk side. Without surrogates, they stop at the root and get its rate, 0.198. Neither knows what the data say: that non-responders churn more than average. Surrogates are designed for values missing at random, where another input can stand in; when the missingness is the signal, they throw it away.

Three ways to handle the gaps

The alternatives to surrogates:

  • Imputation: fill the gaps with a typical value, such as the training median. Simple, but it pretends the non-responders are average.
  • A missingness code: fill the gaps with a value outside the real range (here -1, below every real score), and add an indicator column. A tree can then split the missing cases off on their own, on either input, whenever that helps.

Your turn. Grow a tree three ways, with surrogates, with median imputation, and with the code and indicator, and compare their validation AUCs.

Code the gaps as -1.

f <- churned ~ . - sales_rep
med <- median(train$satisfaction, na.rm = TRUE)
impute <- function(d) { d$satisfaction[is.na(d$satisfaction)] <- med; d }
code <- function(d) {
  d$sat_missing <- factor(ifelse(is.na(d$satisfaction), "yes", "no"))
  d$satisfaction[is.na(d$satisfaction)] <- -1
  d
}
t_sur <- rpart(f, data = train, method = "class", cp = 0.005)
t_imp <- rpart(f, data = impute(train), method = "class", cp = 0.005)
t_code <- rpart(f, data = code(train), method = "class", cp = 0.005)
c(surrogates = auc(predict(t_sur, valid)[, "yes"], valid$churned),
  median = auc(predict(t_imp, impute(valid))[, "yes"], valid$churned),
  code = auc(predict(t_code, code(valid))[, "yes"], valid$churned))

0.762, 0.768 and 0.766: practically the same. On these data, the satisfaction score is mostly redundant (the complaints and late deliveries that drive it are already in the model), so how its gaps are handled hardly matters. That’s often the case, and worth checking before investing in elaborate imputation. When an input with informative gaps matters more, as the financial ratios do in this module’s project, the code-and-indicator approach is usually the safest for trees, because it lets the tree decide.

Your turn. Trees only use the order of a numeric input. Check that taking the log of the volume (a monotone transformation) leaves the tree’s predictions unchanged.

The log tree needs the log-transformed validation data, valid_log.

f <- churned ~ . - sales_rep
t_raw <- rpart(f, data = train, method = "class", cp = 0.005)
train_log <- train; train_log$volume_t <- log(train$volume_t)
valid_log <- valid; valid_log$volume_t <- log(valid$volume_t)
t_log <- rpart(f, data = train_log, method = "class", cp = 0.005)
identical(predict(t_raw, valid), predict(t_log, valid_log))

TRUE. A split at “volume < 120 t” and one at “log(volume) < 4.79” send exactly the same accounts left. So trees need none of the transformations that regression needs (logs, standardizing, dealing with skew), and outliers in an input can’t pull a split around. That robustness is a large part of why trees are so easy to use on raw business data. The target is different: for regression trees, a log transformation of the target does change the tree.

Sixty sales reps

Your turn. Find how many training accounts each sales rep has, and the range of the reps’ churn rates.

The range of the reps’ rates: range(rate_rep).

n_rep <- table(train$sales_rep)
rate_rep <- tapply(train$churned == "yes", train$sales_rep, mean)
print(summary(as.numeric(n_rep)))
round(sort(rate_rep, decreasing = TRUE)[1:6], 3)
round(range(rate_rep), 3)

Each rep has 21 to 47 training accounts (33 on average), and their churn rates run from 4.0% to 44.1%. With about 33 accounts and a true rate near 20%, a rep’s observed rate has a standard error of about \sqrt{0.2 \times 0.8 / 33} = 7 points, so a spread from 4% to 44% is mostly noise. (Because these data are simulated, we know the truth: three reps, R07, R23 and R41, really do lose customers. R07 and R23 top the list; R41 isn’t in the top six, and R10, R20 and R40 are there by chance.)

Smoothed target encoding replaces each level with a number: its churn rate, shrunk toward the overall rate in proportion to how little data it has,

\text{encoded} = \frac{n_k \bar y_k + m \, \bar y}{n_k + m},

where n_k and \bar y_k are the level’s count and churn rate, \bar y the overall rate, and m a smoothing constant: a level with m accounts is pulled halfway. It’s the partial pooling of Module 5’s hierarchical models, in one line. The encoded rep becomes a single numeric input with one sensible order, instead of 60 levels with 5.8 \times 10^{17} groupings.

Your turn. Encode the reps with m = 20, and look at the top six and the new range.

The denominator is n_k + m.

n_rep <- table(train$sales_rep)
rate_rep <- tapply(train$churned == "yes", train$sales_rep, mean)
prior <- mean(train$churned == "yes")
m <- 20
enc <- (n_rep * rate_rep + m * prior) / (n_rep + m)
round(sort(enc, decreasing = TRUE)[1:6], 3)
round(range(enc), 3)

The range shrinks to 11.0% to 35.1%, and R07 stays clearly on top (35.1%), with R23 second (26.3%). R10 is now level with R23 at 26.2%, and R41, the third truly bad rep, ranks only 25th of 60. Shrinkage tames the noise, but it can’t create information that isn’t there: with 32 accounts each, the data can find the worst rep, and not much more.

There’s a trap in using the encoding: a training account’s own outcome is part of its rep’s rate, so the encoded input contains a little of the target. That’s leakage, and with small levels it’s not little. The fix is to encode out of fold: split the training set into folds, and encode each fold’s accounts with rates computed from the other folds. Validation accounts are encoded with the full training rates.

Your turn. Encode the reps out of fold (5 folds), grow a tree with the encoded rep in place of the raw one, and find its validation AUC and whether it uses the encoded rep.

Encode fold j’s accounts: train[fold == j, ].

m <- 20
encode <- function(from, to) {
  n <- table(from$sales_rep); r <- tapply(from$churned == "yes", from$sales_rep, mean)
  e <- (n * r + m * mean(from$churned == "yes")) / (n + m)
  as.numeric(e[as.character(to$sales_rep)])
}
set.seed(8082)
fold <- sample(rep(1:5, length.out = nrow(train)))
train_e <- train; valid_e <- valid
train_e$rep_rate <- NA_real_
for (j in 1:5) train_e$rep_rate[fold == j] <- encode(train[fold != j, ], train[fold == j, ])
valid_e$rep_rate <- encode(train, valid)
t_enc <- rpart(churned ~ . - sales_rep, data = train_e, method = "class", cp = 0.005)
c(auc = auc(predict(t_enc, valid_e)[, "yes"], valid$churned), uses_rep_rate = "rep_rate" %in% t_enc$frame$var)

A validation AUC of 0.762, the same as without the reps, and the tree doesn’t split on the encoded rep at all (uses_rep_rate is 0, FALSE). Encoded honestly, the reps carry too little reliable signal to earn a split, which is the right answer: their effect is real but too thinly spread to estimate well from 1,962 accounts. Compare the next two challenges, where it goes wrong.

NoteGo deeper: other ways to handle many levels

Besides target encoding: lumping rare levels into an “other” level (forcats::fct_lump_min() does it), which helps when a few levels are big and many tiny; grouping by domain knowledge (reps into regions or teams), often the best option; frequency encoding (the level’s count), useful when size matters; and hierarchical models (Module 5), which estimate each level’s effect with partial pooling inside the model, the principled version of smoothed encoding. For trees specifically, ctree (Lesson 7) and CHAID (Lesson 6) test a many-level factor fairly, and C5.0 and some implementations of gradient boosting have their own handling. Micci-Barreca’s “A Preprocessing Scheme for High-Cardinality Categorical Attributes” (SIGKDD Explorations, 2001) introduced smoothed target encoding.

Challenge round

Challenge 1 · The leak. Encode the reps with their raw, in-sample training churn rates (no smoothing, no folds), grow the tree, and compare its training and validation AUCs and the encoded rep’s importance.

Predict the encoded validation data, valid_l.

rate_rep <- tapply(train$churned == "yes", train$sales_rep, mean)
train_l <- train; valid_l <- valid
train_l$rep_rate <- as.numeric(rate_rep[as.character(train$sales_rep)])
valid_l$rep_rate <- as.numeric(rate_rep[as.character(valid$sales_rep)])
t_leak <- rpart(churned ~ . - sales_rep, data = train_l, method = "class", cp = 0.005)
c(train_auc = auc(predict(t_leak, train_l)[, "yes"], train$churned),
  valid_auc = auc(predict(t_leak, valid_l)[, "yes"], valid$churned),
  importance = unname(t_leak$variable.importance["rep_rate"]))

A training AUC of 0.833 and a validation AUC of 0.758, lower than the honest tree’s 0.762, with the leaky encoded rep as an important input (17.9). In the training data, each account’s own churn is part of its encoded value, so the encoded rep looks predictive; on new accounts, it isn’t. This is one of the most common leaks in practice, because target encoding is so useful.

Challenge 2 · The raw factor. Grow the same tree with the raw 60-level sales_rep factor, and find its validation AUC.

Fit on train, with every input.

t_raw <- rpart(churned ~ ., data = train, method = "class", cp = 0.005)
auc(predict(t_raw, valid)[, "yes"], valid$churned)

0.716, the worst of all the versions: five points below leaving the reps out (0.762). CART searches the 60 levels for groupings at every node, finds ones that fit the training accounts’ noise, and spends splits on them that new accounts don’t follow. Out of the three ways to use the reps, ignoring them, encoding them honestly, or handing the raw factor to CART, the last is the only one that hurts.

Quick quiz

1. Accounts without a satisfaction score churned more. What does that mean?

A model can use the gap itself, with a missingness indicator.

2. What is a surrogate split?

Its adj measures how much better it does than the majority direction.

3. When are surrogate splits a poor way to handle missing values?

Surrogates route missing cases like similar complete ones, throwing the signal away.

4. Why didn’t taking the log of the volume change the tree?

Trees need no scaling or transformation of their inputs.

5. What does smoothed target encoding do with a sales rep who has few accounts?

(n_k \bar y_k + m\bar y)/(n_k + m): partial pooling.

6. Why encode out of fold?

In-sample encoding gave a training AUC of 0.833 and a worse validation AUC.

Wrap-up

You can now deal with gaps and messy categories in tree models. Here’s what you’ve learned:

  • Missingness can be information: accounts without a satisfaction score churned at 22.7%, against 18.5%.
  • Surrogate splits route missing cases by other inputs; here the best surrogate barely beat the majority, and sent every gap to the low-risk side.
  • Surrogates, median imputation and a missingness code gave validation AUCs of 0.762, 0.768 and 0.766: when the input is redundant, the choice hardly matters.
  • Monotone transformations don’t change a tree.
  • The 60 reps’ churn rates ran from 4% to 44%, mostly noise. Smoothed target encoding with m = 20 shrank them to 11% to 35%.
  • Out of fold, the encoded rep earned no split (AUC 0.762); in-sample, it leaked (training 0.833, validation 0.758); as a raw factor, CART overfitted it (0.716).

NoteKey words from this lesson
Surrogate split
A split on another input that best mimics the primary split, used to route cases whose primary input is missing.
Missing not at random
Missingness that depends on the unobserved value itself, so that the gap carries information.
Missingness indicator
A 0/1 input recording whether a value was missing.
High-cardinality categorical input
A categorical input with many levels, such as a sales rep or a postcode.
Target (mean) encoding
Replacing each level of a categorical input with the average target for that level.
Smoothing (shrinkage)
Pulling a level’s estimate toward the overall average, more strongly when the level has few cases.
Out-of-fold encoding
Computing each training case’s encoding from the other folds only, so that its own target isn’t used.
